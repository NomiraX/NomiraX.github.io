流式输出：让 Agent 边执行边反馈

文章发布时间:
2026-11-16

流式输出省下的不是时间，是等待时的空白。总耗时可能一点没变，但用户在第一秒就看见了东西在动——而 agent 比聊天更需要这件事，因为它可能要调十次工具才给你一句回答。

整理自 B 站视频：流式输出：让 Agent 边执行边反馈

一个必须回答的体验问题

传统 HTTP 是「一问一答」：客户端发请求，服务端算完，一次性返回，连接结束。简单、稳定，很适合静态资源。

但大模型在 decode 阶段是逐 token 生成的，要凑出一段完整回答得预测几十上百次，耗时半分钟甚至更久。如果还按老规矩等它全生成完再返回，用户在那半分钟里既看不到字，也分不清三种完全不同的状况：程序挂了、网络断了、还是模型正在努力。体验上是灾难。

所以大模型产品几乎无一例外都用流式响应：服务端开始生成就往外吐，吐几个 token 就返回一次，客户端收到一段就渲染一段。用户立刻知道「它在工作」，还能边读前面边等后面。

一个容易被忽略的澄清：流式不缩短总生成时间，它缩短的是「首字出现的时间」（TTFT）。但人对等待的感受几乎完全由这个指标决定——先看到字，剩下的等待就不再是煎熬，而是阅读。

SSE：一条只往一个方向流的水管

服务端推送事件用的协议叫 SSE（Server-Sent Events）：基于普通 HTTP 的事件推送机制。客户端发一次请求，服务端把响应流保持打开，随着内容生成不断往里写事件帧，客户端逐个监听、逐个解析。

组成 含义
data: 前缀 这一帧的负载，多行 data: 会被拼成一个字符串
两个换行 \n\n 帧边界，一个空行表示这帧结束（最关键的一条）
event: 自定义事件名，客户端可据此分派（不写也能靠 payload 里的 type 分派）
id: 事件 ID，断线重连时客户端会带上 Last-Event-ID，服务端可据此补发
retry: 重连间隔建议值

因为是纯文本、走 HTTP、单向推送，SSE 省掉了 WebSocket 的握手、心跳和双向状态管理。聊天这种「服务端一直说、客户端偶尔说一句」的场景，单向刚好够用。

服务端：把生成过程包装成事件流

用 FastAPI 写一个最小的例子。核心思路只有一句：异步生成器不断 yield 事件，外面套一层把它格式化成 SSE 帧。

三个值得记住的点：

  1. 事件是业务对象，不是字符串拼接。event_stream() 里只关心「发生了什么」，sse() 才关心「怎么变成字节」——这层分离后面会救你。
  2. StreamingResponse 接受任何异步迭代器，每 yield 一次就往客户端 flush 一次。想让它真的「边生成边到」而不是被攒起来，记得关掉反向代理和 CDN 的缓冲。
  3. 整理一下类型：这个例子已经是三个事件的骨架——开始、增量、结束。真实 agent 还会再加工具调用、思考、错误、需要用户输入等类型。

客户端：为什么 EventSource 不够用

浏览器原生有 EventSource，专门接收 SSE，用起来极简。但它在真实场景里有两个硬伤：

限制 后果
只能发 GET 请求 prompt、历史消息、鉴权都要塞进 URL
URL 长度有限制 多轮对话和长 prompt 很快就超了

大模型请求里既有多轮历史（长），又有 API Key 之类的敏感信息（不该进 URL 和日志）。所以实践中普遍用 fetch + ReadableStream。

几个新手最容易踩的点，视频里都点到了：

  • 忘了 await reader.read()：不加 await 会变成忙等死循环，CPU 直接跑满。
  • done 才是结束信号，不是「读到内容为空」。read() 在没有新数据时会挂起，这正好是我们要的等待。
  • { stream: true } 不能省：一个中文字符在 UTF-8 里是 3 个字节，很容易被切在两次 read() 之间。开启 stream 模式，decoder 会把不完整的字节留在内部缓冲，等下一个分片拼上。
  • 必须自己做帧重组：一次 read() 拿到的可能是半个 data: 行、半帧、或者三帧连在一起。视频里的 demo 为了讲清主线是直接 append 的，真做产品得按 \n\n 切。
  • 最后要 flush：decoder.decode() 不带参数再调一次，把缓冲区里剩下的字节吐出来。

从「输出文本」到「输出事件」：协议才是重点

只显示文字的聊天，上面这点代码就够了。但 agent 不一样：它会调搜索、调各种工具、思考、汇报进度。前端必须能分清「这行字是要展示给用户的回答」还是「这是我刚调完一个工具的状态」——这需要服务端和客户端事先约定事件类型，也就是协议。

业界的默认参照是 OpenAI 的约定，各家基本都往这个形状上靠：

type 含义 前端典型反应
run.started 本次运行开始 清空上次结果，显示「思考中」
message.delta 回答的增量片段 追加到正文
reasoning.delta 思考过程的增量 折叠面板里滚动
tool.started 开始调用某工具（带 tool_name） 显示「正在执行：web_search」
tool.completed 工具返回 收起进度，可展开看原始结果
agent.handoff 交接给子 agent 显示「已转交 ×× 处理」
run.completed 运行正常结束 移除进度条，定格
run.failed 运行失败（带错误信息） 展示错误 + 重试按钮

关键转变在这里：界面不再由一句 prompt 决定，而由一串类型化事件驱动。服务端在事件里告诉你现在处于什么阶段，前端按 type 分派到不同的组件去渲染。这比「解析自然语言猜它想干什么」可靠得多，也是 agent 能做出「像应用」而不是「像聊天框」的前提。

更进一步：让服务端决定界面（a2ui）

文本和状态之外，还有一类事件需要用户当场做选择：用哪种语言写这段代码、选哪个航班、确认要不要删文件。如果只让模型输出一句「请告诉我你选哪个」，用户就得手打回复，格式全靠自觉，前端也没法校验。

于是有了 agent-to-UI 的思路：服务端在事件里直接携带「该渲染什么控件」的声明，客户端照着渲染，用户点选后把结果作为一条消息交回给 agent。

客户端收到就渲染成一组单选按钮（multiple: true 则渲染多选），用户点完把选中值回传，模型接着按这个前提往下答。这样交互是结构化的：不需要解析自由文本，不会出现「我说要 Python，它却理解成 PHP」，选完还能直接进入下一步。

这也是为什么很多产品的选项卡片、确认按钮、表单看起来「不像聊天」——它们就是被这些事件渲染出来的。后面讲 human-in-the-loop 时还会回到这套机制。

CLI 里的流式：同一件事，换个终端

流式不是 Web 专属。在命令行里同样需要「边生成边显示」，而 CLI 的 SDK（OpenAI 官方库）已经把它做成一个参数：

三个细节：

  • stream=True 是开关，返回的是一个可迭代的事件流，而不是一个完整对象。
  • end="" + flush=True，缺一个就看不到「逐字蹦」的效果：end="" 保证不换行，flush=True 保证不攒在缓冲区里。
  • 按类型分派，和前端一模一样：delta.content 打印正文，delta.tool_calls 拼装工具调用的展示，错误走 stderr（print(..., file=sys.stderr)）以便和正常输出分开。

想调试自己收到了什么事件，直接把原始事件打出来即可——在浏览器 Network 面板里看到的 data: 帧，和 CLI 里打印的事件对象，本质是同一份东西。

三层结构，记住这个分工

层 负责 关键点
传输层 SSE / text/event-stream 一次 HTTP 响应里持续写帧，\n\n 切帧，关掉代理缓冲
事件层 事件协议（type + 结构化 data） 把「agent 在做什么」变成可渲染的类型化数据
界面层 Web / CLI / 桌面 按 type 分派到文本、进度、控件；用户操作回传成消息

写 agent 应用时，这三层塌在一处是最常见的返工原因：把渲染逻辑写进服务端字符串、或者在前端靠正则猜状态，等加了第二个工具就全崩。

这一课真正的收获

  1. 流式的价值是首字时间，不是总时间。体验由 TTFT 决定。
  2. SSE 只是水管，事件协议才是灵魂。前者是十行代码，后者决定你的产品能不能长出聊天框以外的东西。
  3. fetch + ReadableStream 是主流选择，EventSource 的 GET 限制在大模型场景基本不可用。
  4. 字节解码和帧重组是两个独立的坑：UTF-8 跨块用 TextDecoder 的 stream:true，半帧/多帧用按 \n\n 切。
  5. 中断要能真的停下来，AbortController 在前端只解决一半，服务端还得配合取消，否则只是看不见但还在烧钱。

下一课开始进入 agent 的核心能力——怎么让模型学会使用工具。流式输出的这套事件机制，正是工具调用能被「看见」的基础：工具开始时发一个 tool.started，返回时发 tool.completed，用户才知道它到底在干什么。
