用 50 行代码跑通一个 Agent 循环

Created2026-11-15|Updated2026-11-15|技术
|Post Views:

Agent 的门槛比听起来低得多：一个模型、一份工具清单、一个不断追加的消息列表、一个 while 循环，就能让它自己去查资料、拿结果、再回答。

贯穿整个系列的是一个 personal agent 项目：能回消息、能写代码、能沉淀能力，本质上是个人的数字分身。

视频里有个判断值得记下来：agent 开发正在从“高级岗位的技能”变成“通用基本功”，校招、社招、算法岗都会被问到，而且问得越来越深——“会用 RAG”远远不够，会问工具怎么设计、循环怎么终止、上下文怎么控制。

agent 拆成四块

去掉各种花哨的定义，一个能跑起来的 agent 只有四部分：

组成 职责
大模型 理解任务、分析现状、决定下一步
工具 和外部世界交互：查数据库、调接口、读写文件、执行命令
上下文 模型这一轮能看到的全部信息：系统提示、历史、工具定义与结果
循环 一次搞不定就多轮迭代，直到模型认为可以给答案

只调一次 API 得到一段文本，那不是 agent，那是问答。agent 的关键在于“模型输出的是一个决策，而这个决策需要外面的程序去执行，执行结果再回到模型眼前”。

ReAct：一轮循环长什么样

ReAct = Reasoning + Action，思考加行动。它描述的是一轮里发生的事：

  1. 模型读当前上下文，分析已经有什么、还缺什么；
  2. 缺什么就决定调哪个工具、传什么参数（action）；
  3. 程序执行工具，把结果塞回上下文（observation）；
  4. 模型再看一眼：够了吗？够就给答案，不够继续第 1 步。

对人来说这就是“查一下、看一眼、再查一下”的过程，agent 只是把这个过程写成了循环。要注意第 3 步的执行者是你的程序，不是模型。模型只负责说“请帮我调 get_price，参数是蓝牙耳机”，真正的函数调用发生在模型外面。这是初学最容易混淆的一点。

消息列表就是 agent 的状态

模型 API 是无状态的：每次请求你发什么它就看什么，上一轮说过的话它一概不知。所以 agent 的“记忆”不在模型里，而在你维护的那个 messages 数组里。

数组里每条消息都有一个 role，各司其职：

role 谁写的 作用
system 你 角色设定与行为约束，放第一条，整个循环都生效
user 用户 这次任务的起点，也是循环要推进到的目标
assistant 模型 模型的回复；带 tool_calls 时相当于 ReAct 的 action
tool 你的程序 工具执行结果，相当于 observation；靠 tool_call_id 和上面的 action 对应

有三个细节必须做对，否则一定报错：

  • 模型返回的那条 assistant 消息要原样追加回数组，包括里面的 tool_calls 和它们的 id；
  • 模型一次可能发起多个工具调用（并行调用），每个都要执行，每个的结果都要用对应的 tool_call_id 回填；
  • tool 消息的 content 必须是字符串，字典要先 json.dumps。

漏掉其中一个 tool_call_id，OpenAI 兼容接口会直接返回 400：它认为你欠它一条结果。

工具怎么描述给模型

模型没法猜你的函数长什么样，所以要用它认识的标准格式告诉它有哪些工具、每个工具干什么、要什么参数。本质是一段 JSON Schema：

写工具描述的经验：

  • name 用语义化的动词短语，模型是靠名字和描述建立联想的；
  • description 要写清什么时候用和有什么限制，只写“查询价格”太弱，加上“一次只查一个”能明显减少乱传参数；
  • parameters 里的 description 同样重要，它是模型填参数时的唯一依据；
  • 工具定义会随每次请求一起进上下文，工具多了输入 token 会明显变贵，别把一套 API 全塞进去。

几处值得单独说：

  • model_dump(exclude_none=True) 是 OpenAI SDK 提供的便捷方法，能把 pydantic 对象转成可以直接回传的字典，且不塞进一堆 null；
  • 循环上限 5 轮是必需的护栏，模型有概率陷进“再查一次”的死循环；
  • else 分支挂在 for 上，只有循环跑完没 break 才执行，正好用来处理“超轮数”。

跑起来是什么样

第一轮模型不会直接回答，而是同时发起两个 get_price 调用——一次查蓝牙耳机，一次查降噪耳机。程序依次执行，把两条结果回填：

第二轮模型看到了两个价格，tool_calls 为空，直接给结论：蓝牙耳机更便宜，便宜 170 元，并说明这是根据查询结果算出来的，不是估的。

注意这个结论有依据，是因为 299 - 129 这个算术建立在两个真实返回值上。如果把工具返回值改成错的，模型会跟着错——它只对上下文里的数字负责。

第二个例子：查真实天气

比价用的是假数据，第二个 demo 换成真实接口。任务是“对比北京和上海现在哪个更热，给穿衣建议”，工具只有两个：

  • search_city：城市名 → 经纬度；
  • get_weather：经纬度 → 当前天气。

注意这里的依赖关系：天气 API 只认经纬度，所以模型必须先查坐标再查天气。这正好是 agent 比单次调用强的地方——它自己排出了调用顺序，你只给了目标和两个工具。

这次演示里发生了一件更有意思的事：第一次调天气接口时网络出错，失败结果作为 observation 回到了模型。模型读到错误信息，判断是网络问题，把两个城市的英文名重新转了一遍（中文名直接调外网 API 常失败），又发起一轮调用，第二次成功。

这是本节最实用的一课：工具失败时不要把异常抛出去终止流程，把错误当成 observation 返回给模型。模型能读懂 error 字段并自行更换参数重试，这比你在外面写一堆重试逻辑更省事。当然，能重试几次、重试哪类错误，还是要你来兜底。

这 50 行里还缺什么

能跑通和能用之间隔着这些东西，也是后面几课要补的：

  • 错误处理：工具抛异常要转成结构化错误回填，而不是让整个循环崩掉；
  • 参数校验：模型给的 JSON 可能缺字段、类型不对，json.loads 之前最好做 schema 校验；
  • 并发：多个 tool_calls 目前是串行执行，互相独立的调用应该并发；
  • 流式输出：真实产品里要边生成边显示，stream=True 后还要处理流式返回的 tool_calls 分片；
  • 计费与观测：每轮记 prompt_tokens、completion_tokens 和其中的 cached_tokens，否则不知道钱花在哪；
  • 终止条件：除了轮数上限，还应该有总 token 预算、总耗时上限；
  • 安全：工具参数是模型生成的，拼 SQL、拼 shell、拼路径之前必须校验和转义，能力越强的工具越要限制参数——这是生产环境里出事最多的地方；
  • 权限与审批：删文件、发消息、下单这类有副作用的操作，要有人工确认或白名单。

小结

三句话：

  1. agent 的骨架是“消息列表 + 循环”，模型负责决策，你的程序负责执行，执行结果回到列表里。
  2. 消息的 role 和 tool_call_id 是协议层，写错一处整条链路就断。
  3. 五十行能跑通，但错误处理、并发、计费、权限这四件事决定它能不能上生产。
