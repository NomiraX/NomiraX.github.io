Agent = LLM + Harness

文章发布时间:
2026-11-15

大模型给了 agent 一个会思考的大脑，harness 给了它手脚、记忆、循环和运行时。少任何一样，它都只是个会聊天的接口。

整理自 B 站视频：Agent= LLM + Harness

agent 这个词其实很老

中文译作“代理”或“中介”：能替你思考、替你办事的东西。人类对这个概念的想象比计算机早得多——从神话里的机关人，到织布机，到工业机械臂，都是“按预定程序替人干活”，但没人叫它们 agent，因为它们不能思考，只能执行写死的步骤。

后来的路是一点点补上“理解”和“决策”：

阶段 代表 补上了什么 还缺什么
预设程序 机械臂、织布机 执行力 不会思考
语音助手 Siri 能听懂一部分自然语言 指令仍是预设的，能力有限
搜索与博弈 AlphaGo 在巨大策略空间里自主决策 只在一个领域内成立
对话模型 ChatGPT 通用理解、生成复杂内容 只能说话，办不了事
工具调用 2025 年之后的 agent 能操作外部世界，围绕目标多步执行 可靠性与安全问题

一个更实用的定义：能感知环境、能思考决策、能采取行动，并反复迭代直到目标完成。按这个标准，AlphaGo 算 agent，但它是特定领域的；今天讨论的 agent 默认由大模型驱动，所以具备通用的世界理解和通用的决策能力。

这也解释了为什么 2025 年之后 agent 突然普及：模型能力早就够了，缺的是“手脚”——工具调用协议成熟之后，对话才变成行动。

只有模型接口，不是 agent

这一课做了三个很干净的实验，说明模型本身缺什么。

实验一：让它读本地文件。 给它一个 PRD 的文件名，让它评审。模型的回答是：我读不到你本地的文件，请把内容贴过来。它会思考，但没有手脚，拿不到文件系统里的任何东西。

实验二：连续两次调用。 第一次告诉它“评审 PRD 时重点看数据指标是否有依据”，它回答“收到”。第二次只问“我刚才让你重点看什么”，它回答“你还没有告诉我重点看什么”。它把上一句忘得干干净净。

实验三：把历史拼回去。 这一次把第一次的 user 消息、第一次的 assistant 回复、第二次的追问一起发过去，它立刻答对了：“你刚才让我重点关注 PRD 里的数据指标是否有依据。”

结论很清楚：模型没有记忆，所谓“它记得”只是你把历史重新贴了一遍。这件事不只是实现细节——API 无状态本身也是隐私设计，否则 A 用户的内容会泄漏给 B 用户。

到这里，模型比 agent 少的三样东西就清楚了：

  • 工具：跟外部世界交互的通道；
  • 循环：一次调用不够，要能多轮推进；
  • 上下文：把历史喂回去，才有连贯性。

还差一层：运行时

工具、循环、上下文凑齐，demo 能跑，但离“能用”还差一层。真实的 agent 会遇到：

  • 工具调用超时、报错、返回垃圾数据，怎么处理；
  • 长任务跑到一半进程挂了，状态存哪；
  • 工具改动了外部环境（写文件、下单、发消息），怎么隔离、怎么回滚；
  • 危险操作之前要不要人确认；
  • 出了错怎么复盘，钱花在哪。

这些不属于模型、也不属于单个工具，而是运行时（runtime）的职责。所以本课给的公式是：

harness（马具、挽具）这个词很形象：模型是马，harness 是把它的力气接到车上的那套东西。业界也有另一种等价说法——agent = 大模型 + 工具 + 记忆 + 规划——维度不同，指的是同一件事。

在这个底座上还能继续往外扩：memory 存跨会话的信息，RAG 接外部知识，skill 封装做事的套路。它们都属于 harness 的范畴，因为它们的共同点是“模型之外、为了让模型能干活而存在的一切”。

判断一个框架是不是 harness，看它有没有这几件事就够了：

职责 具体内容
上下文组装 系统提示、历史裁剪、工具定义注入、知识召回
工具执行 参数校验、并发调度、超时重试、错误回填
循环控制 终止条件、轮数预算、token 预算
运行时 会话状态、沙箱、权限、人工审批、日志与追踪

大模型、Workflow、Agent：谁决定路径

这三个词经常混着用，判断标准只有一个：执行过程由谁决定。

还是 PRD 评审这个任务，三种写法对比：

裸模型：读 PRD → 拼进提示词 → 让它指出最多三个问题。结果很泛：它不知道点击率到底多少，只能说“请明确基线”；也没有核实用户反馈的依据，建议停留在“可以做个 AB 实验”。开发者明明知道该查数据，但没写进提示词，模型也不会主动要求。

Workflow：把步骤写死成代码——读 PRD、检查完备性、生成三条评审意见，每个节点调一次模型。结果比裸模型靠谱，因为它有固定工序。但工序是人写的，人忘了“查数据”这一步，结果照样粗略；要加一步，就得改代码。

Agent：只告诉它目标和边界——“你是 PRD 评审助手；PRD 缺数据支撑时，去查指标；最多三步”。把 read_doc 和 query_metric 两个工具交给它，路径由它自己排。结果它先读文档，再连续查了三个指标，甚至还多做了一次无关的搜索。

维度 裸模型 Workflow Agent
谁决定执行路径 开发者（只调一次） 开发者（预编排） 模型（在目标和边界内）
确定性 低，取决于提示词 高，每次一样 中，可能漏步也可能多做
能力边界 窄，只处理输入里的信息 中，工序之外就卡住 宽，能组合工具应对新情况
调试难度 低 低 高，路径不固定
适合的场景 单步生成、结构化抽取 流程稳定、要求可预测 目标明确但路径不确定

视频里说得很实在：确定性下降是 agent 的代价。它可能忘查某一步，也可能顺手调了不该调的接口。所以工程上不是“有了 agent 就不要 workflow”，而是反过来——把确定的小步骤固化成 workflow，让 agent 去调度它们：

大任务拆成小任务，小任务里有幻觉风险的环节交给代码，需要判断的环节交回模型。这个组合在真实业务里比纯 agent 稳得多。

一个 coding agent 修 bug 的完整路径

把上面的东西套一遍会更清楚。用户只给一句“修一下这个 bug”，agent 要做的是：

  1. 读代码，理解目标，定位原因；
  2. 修改文件；
  3. 跑测试，看结果对不对；
  4. 不对就看错误信息继续改，直到通过。

这就是“决策 → 执行 → 观察 → 调整”的循环，和人类开发者一模一样。区别在于：它需要运行时提供真实的开发环境（能跑命令的沙箱）、需要权限控制（不能随便推到远端）、需要状态管理（改了哪些文件要记着）。

所以 agent 开发不是“写好提示词”这么简单，它本质上是围绕大模型构建一套能自主执行、可靠交付的软件系统。这句话里的“软件系统”是重点。

顺着这个公式，要学的就四层

层次 学什么 解决什么问题
基础原理 模型怎么工作、消息怎么组织、最小的 agent 怎么写 能跑起来
行动能力 工具设计、MCP、RAG、记忆、skill 能拿到对的信息、能做对的事
架构与运行 plan、workflow、单 agent 与多 agent、harness、沙箱、状态管理 能做复杂任务、能跑稳
工程化 评测、可观测、权限、成本、交互 能从 demo 变成产品

第一层对应上一篇的五十行代码；后面三篇笔记会陆续展开。

小结

  1. agent 不是模型的新能力，而是模型外面那套系统的名字；Agent = LLM + Harness 是最好用的拆解工具。
  2. 模型无状态、无手脚、无终止条件，这三件事分别对应上下文、工具、循环。
  3. 选择用模型还是用 workflow，看的是“执行路径由谁决定”，而成熟的做法是让 agent 调度 workflow，而不是二选一。
