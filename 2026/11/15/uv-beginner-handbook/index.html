uv 入门：从装好到把项目交出去

文章发布时间:
2026-11-15

参考：B 站《新手必看！Python 包管理神器 UV》（井水）与《我为什么弃用 Conda，改用 uv 来管理 Python 虚拟环境》。文中命令与输出均在 uv 0.13.8 / Windows 上复核过，与早期版本有出入的地方单独标出。

1. 概述

uv 是一个用 Rust 写的 Python 工具，把三件事收进同一套命令：管 Python 版本、建虚拟环境、管项目依赖。官方给的说法是安装速度比 pip 快 10~100 倍；实测里「快」主要发生在缓存命中和依赖解析上，第一次下载并不夸张。

它解决的真正痛点，用过 conda 的人最清楚：

  • 每建一个环境都要起名，机器上堆到几十个环境后，看到 myenv-2 根本想不起它属于哪个项目；
  • 新环境要重新装一遍包，哪怕隔壁环境昨天刚装过；
  • 每次都要 conda activate，还容易激活错；
  • requirements.txt 里只写 >=，别人装出来的版本和你不一致，出问题难复现；
  • 越来越多开源项目（例如 index-tts 2）直接用 uv 管理，不会读它的项目，连环境都搭不起来。

uv 的答案是把环境绑回项目：.venv 就在项目目录里，环境名就是项目名；所有包版本进全局缓存，新环境直接硬链接复用；uv.lock 把精确版本和哈希钉死；uv run 免激活。快只是副产品，核心是环境跟着代码走。

快的原因拆开是三件事：依赖解析一次算完整张图（pip 的解析器重复计算多）、下载并行（pip 是一个装完再下一个）、缓存与硬链接（同一份 wheel 不重复落盘）。uv 没有发明新格式，pyproject.toml、wheel、venv 目录结构都还是标准那套，它改变的是工作流。

需要划清的边界：uv 只管 Python 侧。项目里一旦混进 CUDA、编译工具链、R 或系统库这类非 Python 依赖，conda 仍然是更省心的选择——它本来就是多语言的包管理器。

2. 结构拆解

2.1 一个项目里有什么

uv init --no-package --python 3.13 之后，真正要认识的文件是这些：

文件 作用 提交到 Git
pyproject.toml 项目元数据 + 你直接声明的依赖 要
uv.lock 完整依赖图：子依赖、精确版本、下载源、sha256 要
.python-version 项目用的 Python 版本，内容一行，如 3.13 要
main.py 入口脚本，uv init 生成，可改可删 要
README.md 项目说明 要
.venv/ 虚拟环境本体，装好的包都在这里 不要
.gitignore 哪些文件不进版本库 要（若生成）

三个文件的分工值得单独说清：

  • pyproject.toml 写的是宽泛要求：dependencies = ["httpx>=0.28"]，意思是「至少 0.28，越多越好」；
  • uv.lock 写的是精确结论：每个包一行，带 source（从哪个索引站下）、wheels、sha256。它由工具生成，不手改；
  • .python-version 是解释器版本，uv python pin 3.12 改的就是它。

uv init 不带 --no-package 时生成可打包布局（多出 src/<项目名>/ 与构建配置）；不带 --python 时 uv 会挑本机可用的最新解释器，可能直接给出 requires-python = ">=3.15" 这种前沿版本。

阶段 命令 作用

3. 关键概念与术语表

术语 含义
uv Astral 出的 Rust 实现 Python 包/环境管理器，统一管解释器、虚拟环境、依赖
conda 跨语言的包与环境管理器；强在非 Python 依赖（CUDA、系统库、其他语言链）
pyproject.toml 项目描述文件（PEP 621），写元数据与顶层依赖的宽泛要求
uv.lock 锁文件，记录完整依赖图、精确版本、下载源与哈希，用于复现
.python-version 一行文本，写明项目使用的 Python 版本，uv 与 pyenv 都认
.venv 虚拟环境目录，含独立解释器与 site-packages；不提交、不打包
索引源 / 镜像站 下载包的仓库；国内镜像（清华、阿里云、南大等）是同一批包的副本
UV_DEFAULT_INDEX 环境变量，指定默认索引源；也可用 [[tool.uv.index]] 写进项目
依赖解析 按版本约束算出整张依赖图该用哪些版本，包管理器最耗 CPU 的环节
传递依赖 你装的包自己依赖的包，不直接声明但要跟着装
uv add / uv remove 增删依赖，同时更新 pyproject.toml 与 uv.lock
uv pip install pip 兼容通道，装进环境但不改清单，不可复现
uv sync 按两个清单还原环境，Python 界的 npm install
uv run 用项目解释器执行命令，替代「先 activate 再 python」

5. 批判性分析

conda 的痛点不是「慢」，是「环境无主」。 起名、激活、忘记对应关系，本质是 conda 把环境放在全局命名空间里，而项目在另一个地方。uv 把 .venv 塞回项目目录，用「路径」替代「名字」，这类问题从根上消失。顺带解决了跨环境复用（全局缓存）与版本复现（lock）。

「快 10~100 倍」要加定语。 官方数字通常指解析与缓存命中的场景；首次下载受网络与镜像影响，快两倍就不错。Windows 上缓存与项目不在同一分区时，uv 会退化成完整复制并提示 Failed to hardlink files; falling back to full copy，设 UV_LINK_MODE=copy 只消警告，磁盘占用照样上去。

uv pip 是逃生通道，不是正路。 它装包只进环境、不改 pyproject.toml 和 uv.lock，uv tree 里也看不到——换台机器就复现不出来。临时试一个包可以，正式依赖一律 uv add。

默认行为会改你的文件。 用环境变量设了默认源后，uv add 会把 [[tool.uv.index]] 写进 pyproject.toml；文件里若已有同名表头，TOML 解析直接报 Cannot declare ('tool', 'uv', 'index') twice。要么只留一条，要么用具名索引配 [tool.uv.sources]。

边界清楚：非 Python 依赖它管不了。 带 CUDA、科学计算底层、多语言工具链的项目，conda 仍更省心；uv 只覆盖 Python 这半边。判断标准很简单——项目里有没有「pip/conda 之外的系统级依赖」。

版本差异自己核对。 老版本 uv init 会顺手 git init 并生成 .gitignore；0.13.8 的 uv init --no-package 只给四个文件。截图与本机结果不一致时先 uv --version。

6. 个人思考与应用

从 conda 迁移，分三步走，别一次搬完。 第一步，新项目全量用 uv，先建立手感；第二步，老项目保留 conda 环境，把 uv pip 当作 pip 的加速替代（同一环境里 uv pip install -r requirements.txt 跑通再谈别的）；第三步，确认无误后把依赖迁到 pyproject.toml，彻底脱离 conda。

environment.yml 不能直接转。 conda 的清单里混着 channel、conda 专有包和 pip 段，必须先拆：pip 段抽成 requirements.txt 交给 uv add -r，剩下的系统级依赖继续留在 conda。

GPU / 深度学习项目可以混住。 系统层（CUDA、cuDNN、编译工具链）交给 conda 或系统包管理器，Python 层用 uv 管项目依赖——前提是 uv 指向 conda 那个解释器（uv venv --python <conda 环境里的 python>），别让两套工具各自建一套环境。

CI 用 uv sync --frozen。 --frozen 表示不许改 lock，lock 与 pyproject.toml 不一致时直接失败，正好把「本地随手加了依赖忘了锁」挡在流水线外。Docker 里先 COPY pyproject.toml uv.lock ./ 再 uv sync --frozen --no-dev，最后 COPY . .，改业务代码不会让依赖层缓存失效。

镜像配在哪。 个人机器用 UV_DEFAULT_INDEX 最省事；团队项目写进 [[tool.uv.index]]，让源跟代码走、可 review，代价是项目文件里混进基础设施信息。

Python 版本也钉住。 uv python pin 3.12 配合 .python-version 入库，「我这儿能跑、你那儿语法错」的问题能少一大半——解释器差异比依赖差异更难查。

什么时候先别换。 团队已经用 poetry 且流程成熟、CI 镜像里 pip 缓存调得很顺、项目依赖里有只能在特定环境编译的包时，迁移收益小于风险。可以先只换「装包」这一环，跑顺了再动 lock。
