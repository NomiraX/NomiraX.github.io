从 conda 换到 uv：让环境跟着项目走

文章发布时间:
2026-11-15

参考：B 站《我为什么弃用 Conda，改用 uv 来管理 Python 虚拟环境》（主）与《新手必看！Python 包管理神器 UV》（补）。命令与输出在 uv 0.13.8 / Windows 复核过，与早期版本有出入的地方单独标注。

1. 概述

先摆问题。用 conda 管 Python 环境，几年下来大概会攒出这么几件烦心事：

  • 环境要起名，而名字会忘。 机器上几十个项目就有几十个环境，看到 myenv、py311、test2，确实想不起它属于谁；
  • 新环境要从头装一遍包。 隔壁环境昨天刚装过 requests，这里还得再下一遍；
  • 每次进项目都要 conda activate，还常常激活错；
  • requirements.txt 只写 >=，别人装出来的版本和你不一样，出错时很难对齐；
  • 开源项目越来越多用 uv（例如 index-tts 2），不会读它的项目，连环境都搭不起来。

把这几条翻译成需求，其实就五句话：环境放在项目里、别起名、装得快且能跨环境复用、版本能精确复现、别手动 activate。

uv 正好对着这五条设计。它是 Rust 写的包与项目管理工具，用一套命令替代了 pip、virtualenv、pyenv、pip-tools 的一部分工作，把「Python 版本、虚拟环境、项目依赖」三块统一管起来。官方说法是安装速度比 pip 快 10~100 倍；实际感受取决于缓存与网络，第一次装并不会快一个数量级，但解析和第二次安装快得非常明显。

一句话概括它和 conda 的区别：conda 把环境放在全局命名空间里按名字管，uv 把环境放回项目目录里按路径管。 名字要人记，路径不用。

边界也要先说清：uv 只管 Python 这一侧。项目里一旦混进 CUDA、系统库、其他语言的工具链这类非 Python 依赖，conda 仍然是更合适的选择——那本来就是它的主场。

2. 结构拆解

2.1 两种环境的形态

conda 的环境住在 ~/miniconda3/envs/<名字> 或 C:\Users\<你>\miniconda3\envs\<名字>，跟项目目录没有关系。项目在哪、环境在哪，全靠你脑子里的一张对照表，外加每次 conda activate。

2.2 五条需求分别由什么实现

想要 uv 的做法
环境跟着项目走 .venv 建在项目目录内，路径即身份
不给环境起名 不需要名字，uv 认目录
装包快、跨环境复用 全局缓存 + 硬链接，同一个 wheel 只存一份
版本可精确复现 uv.lock 锁死精确版本、下载源与哈希
不用手动激活 uv run <命令> 直接用项目解释器执行

你在 pyproject.toml 里只声明了 fastapi，但 fastapi 依赖 pydantic、starlette、typing-extensions……这些子依赖全部落在 lock 里。这就是「换台机器也能装出同一套东西」的依据。

.python-version——解释器版本。 内容就一行，例如 3.13。uv python pin 3.12 改的就是它。这一点和 conda 差别很大：conda 环境建好时定的 Python 版本，后面基本不能动，要换只能重建；uv 里随时可以改，uv python pin 一句就切换。

2.5 走一遍

uv venv 之后，.venv 里有两个要紧位置：Scripts\python.exe（Linux/macOS 为 bin/python）是之后真正被调用的解释器；Lib\site-packages\ 是依赖落地的目录。删掉 .venv 等于清空环境，全局 Python 不受影响。

把项目交给别人时，只交 代码 + pyproject.toml + uv.lock。实测一个项目目录 1.88 MB，其中 .venv 占 1.84 MB，自己的代码只有 0.04 MB——环境里全是能从 lock 重装出来的第三方包，且是平台相关二进制，交出去既占地方又用不了。对方在项目目录执行 uv sync，环境就回来了。

3. 关键概念与术语表

术语 含义
uv Astral 出的 Rust 实现 Python 工具，统一管解释器、虚拟环境、项目依赖
conda 跨语言的包与环境管理器，强在非 Python 依赖（CUDA、系统库、其他语言链）
conda channel conda 的软件源（如 conda-forge、defaults），与 pip 的索引源是两套体系
environment.yml conda 的环境导出文件，含 channel 与 conda 专有包，不能直接喂给 uv
pyproject.toml 项目描述文件（PEP 621），写元数据与顶层依赖的宽泛要求
uv.lock 锁文件，记录完整依赖图、精确版本、下载源与哈希，用于复现
.python-version 一行文本，写明项目使用的 Python 版本，uv 与 pyenv 都认
.venv 虚拟环境目录，含独立解释器与 site-packages；不提交、不打包
索引源 / 镜像站 下载包的仓库；国内镜像（清华、阿里云、南大等）是同一批包的副本
UV_DEFAULT_INDEX 环境变量，指定默认索引源；也可用 [[tool.uv.index]] 写进项目
依赖解析 按版本约束算出整张依赖图该用哪些版本，包管理器最耗 CPU 的环节
传递依赖 你装的包自己依赖的包，不直接声明但要跟着装
uv add / uv remove 增删依赖，同时更新 pyproject.toml 与 uv.lock
uv pip install pip 兼容通道，装进环境但不改清单，不可复现
uv sync / uv run 按清单还原环境 / 用项目解释器执行命令

5. 批判性分析

换掉 conda 的真正理由不是「快」，是「环境无主」。 起名、激活、忘记对应关系，本质都是 conda 把环境放在全局命名空间，而项目在另一个地方，两者关系只能靠人脑维护。uv 用目录位置替代名字，这类问题从根上消失；顺带解决了跨环境复用（全局缓存）和版本复现（lock）。速度是这套结构带来的副产品，不是它唯一的价值。

「快 10~100 倍」有前提。 官方数字通常指解析与缓存命中的场景。首次下载受网络和镜像影响，快两倍就不错；Windows 上缓存与项目不在同一分区时，uv 会退化成完整复制并提示 Failed to hardlink files; falling back to full copy，设 UV_LINK_MODE=copy 只是消掉警告，磁盘占用照样上去。

uv pip 是逃生通道，不是正路。 它装包只进环境、不改 pyproject.toml 与 uv.lock，uv tree 里也看不到（实测装完 rich，树里只有原有依赖）。临时试一个包可以，正式依赖一律 uv add，否则「换台机器就复现不出来」的坑照旧。

默认行为会改你的文件。 用环境变量设了默认源之后，uv add 会把 [[tool.uv.index]] 写进 pyproject.toml；文件里若已有同名表头，TOML 解析直接报 Cannot declare ('tool', 'uv', 'index') twice。要么只留一条，要么用具名索引配 [tool.uv.sources]。

它明确不管的那半边，别指望它。 CUDA、cuDNN、编译器工具链、R/Julia 这类非 Python 依赖，uv 没有对应机制；conda 的价值恰在于把多语言、二进制分发（conda-forge）、企业内网镜像一并解决。深度学习项目里这一条经常是决定性的。

迁移不是零成本。 environment.yml 里混着 channel 与 conda 专有包，不能直接转；团队里有人还在用 pip + virtualenv，lock 文件的行为需要先对齐；CI 缓存策略也要跟着改。这些成本要算，但一次性付出、长期收益，和 conda 的环境重建成本不是一个量级。

版本差异自己核对。 老版本 uv init 会顺手 git init 并生成 .gitignore；0.13.8 的 uv init --no-package 只给四个文件。截图与本机结果不一致时，先 uv --version 再对照文档。

6. 个人思考与应用

迁移分三步，别一次搬完。 新项目直接全量用 uv，先建立手感；老项目保留 conda 环境，把 uv pip 当作 pip 的加速替代，跑通再谈别的；确认无误后把依赖迁到 pyproject.toml + uv.lock，彻底脱离 conda。

environment.yml 要拆着看。 先用 conda env export --from-history 拿到你真正显式装过的东西，把其中 pip 段抽成 requirements.txt，交给 uv add -r；剩下的系统级依赖继续留给 conda。混在一起直接转，十有八九装不上。

GPU / 深度学习项目可以两边分治。 系统层（CUDA、cuDNN、编译工具链）交给 conda 或系统包管理器，Python 层用 uv 管项目依赖。前提是让 uv 使用 conda 那个解释器（uv venv --python <conda 环境里的 python>），别让两套工具各建一套环境。

CI 用 uv sync --frozen。 --frozen 表示不许改 lock，lock 与 pyproject.toml 不一致时直接失败，把「本地随手加了依赖忘了锁」挡在流水线外。Docker 里先 COPY pyproject.toml uv.lock ./ 再 uv sync --frozen --no-dev，最后 COPY . .，改业务代码不会让依赖层缓存失效。

镜像配在哪。 个人机器用 UV_DEFAULT_INDEX 最省事；团队项目写进 [[tool.uv.index]]，让源跟着代码走、可 review、可回滚，代价是项目文件里混进了基础设施信息。

Python 版本也入库。 .python-version 提交，配合 uv python install，「我这儿能跑、你那儿语法错」能少一大半——解释器差异比依赖差异更难查。

什么时候先别换。 团队已经用 poetry 且流程成熟、CI 镜像里 pip 缓存调得很顺、项目依赖里有只能在特定环境编译的包，迁移收益小于风险。可以先只替换「装包」这一环，跑顺了再动 lock。
