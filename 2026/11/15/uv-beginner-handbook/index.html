uv 入门：装好、配源、建项目、管依赖、把项目交出去

文章发布时间:
2026-11-15

参考：B 站《新手必看！Python 包管理神器 UV》（UP：井水）。这篇按「从零开始」的真实顺序整理：装 uv → 配国内镜像 → 初始化项目 → 建虚拟环境 → 装第一个依赖 → 看文件怎么变 → 运行 → 打包交给别人 → 其余常用命令。

1. 概述

uv 是一个用 Rust 写的 Python 环境与包管理工具。它想做的事其实很朴素：把过去分散在 pip、virtualenv、pyenv、pip-tools 甚至 poetry 手里的活，收进同一套命令里 —— 装依赖、锁版本、建虚拟环境、管理多个 Python 解释器、跑脚本，都用 uv 开头。

对刚学 Python 的人来说，它最直接的价值不是「快」，而是少装几个工具、少记几套命令：

  • 装包不用先折腾 python -m venv，再 activate，再 pip install；
  • 换 Python 版本不用去官网下安装包、改 PATH，直接 uv python install 3.12；
  • 换电脑 / 交给同事，只要有 pyproject.toml 和 uv.lock，一条 uv sync 就能把环境还原成几乎一样的样子。

快的来源是几个可以分开看的机制：

  1. 依赖解析更快。装一个库时，包管理器要先算出它连同子依赖的整张图该取哪些版本。pip 的解析器历史包袱重，重复计算多；uv 换上更高效的 SAT 风格求解器，一次把整张图算完。
  2. 下载是并行的。pip 默认一个包装完再装下一个，uv 同时下载多个包，网络往返的等待被叠起来。
  3. 缓存与硬链接。uv 把每个包版本的 wheel 存进全局缓存，装进项目时优先硬链接过去，同一份字节不重复落盘，所以第二次装几乎不花磁盘和下载时间。
  4. 没有 Python 层面的启动开销。整个工具是编译好的原生二进制，跑起来不像 Python 写的工具那样先解释再执行。

代价也要说清楚：uv 仍然遵守 Python 生态的既有标准（pyproject.toml、wheel、venv 目录结构都还是原来那一套），它不是新格式；但它对「工作流」有自己的主张，比如默认把依赖写回 pyproject.toml、默认替你管虚拟环境，这些习惯和 pip 时代不太一样。

2. 结构拆解

2.1 一个 uv 项目里都有什么

在空目录里执行 uv init 之后，真正需要认识的文件只有四五个：

文件 作用 要不要提交到 Git
pyproject.toml 项目身份证 + 你直接声明的依赖 要
uv.lock 完整依赖图（含子依赖的精确版本、哈希、下载源） 要
.python-version 这个项目用哪个 Python 版本 要
.venv/ 虚拟环境本体，装好的包都落在这里 不要
main.py 入口脚本（uv init 生成，可改可删） 要
README.md 项目说明，别人怎么用 要
.gitignore 哪些文件不进版本库 要（若生成）

pyproject.toml 是「结论」，uv.lock 是「证据」：前者只记你亲自要的顶层依赖，后者连子依赖、精确版本、下载地址和 sha256 都钉死。两者的关系很像 package.json 和 package-lock.json。

2.2 八个步骤

第一步：装 uv。 官方推荐先装 uv 再由它去装 Python；但多数人电脑上早就有 Python 了，所以也可以反过来，用 pip 装 uv：

装上后如果终端还不认识 uv，关掉重开一个命令行窗口再试。

第二步：配国内镜像。 不改源的话，解析完还要去国外源下载，慢。最省事的做法是设一个环境变量 UV_DEFAULT_INDEX，值是镜像站地址，例如清华源 https://pypi.tuna.tsinghua.edu.cn/simple。Windows 上可以「此电脑 → 属性 → 高级系统设置 → 环境变量 → 新建」手动加，注意值里不要带引号；改完必须重开终端才生效。

第三步：初始化项目。 建个空文件夹，在地址栏敲 cmd 回车（这样打开的命令行工作目录就是当前文件夹），然后：

--no-package 表示只要一个「能跑脚本」的平铺项目，不生成可发布的包结构。生成 pyproject.toml、.python-version、main.py、README.md。不加这个参数，uv 0.13 起默认生成 src/<项目名>/ 的可打包布局，结构更完整，但初学阶段用不上。

第四步：建虚拟环境。

它会在项目下建 .venv/，里面有两个要紧的东西：Scripts/python.exe（或 bin/python）是之后所有命令实际调用的解释器；Lib/site-packages/ 是依赖真正落地的位置 —— 全局 Python 不受污染。

这一步在新版本里其实可以省：uv add 发现没有 .venv 会自己建一个。显式写 uv venv --python 3.12 的意义在于指定解释器版本。

第五步：装依赖。

uv add 会做四件事：解析整张依赖图、下载、装进 .venv、把顶层依赖写回 pyproject.toml。装完后 uv tree 能看依赖树：

只装一个包，实际进来五个 —— 另外四个是 requests 的子依赖，它们会被记进 uv.lock，不会出现在 pyproject.toml 的 dependencies 里。

第六步：运行。

等价于「用 .venv 里的 Python 执行 main.py」，但不需要先 activate。uv run 还会在运行前检查环境是否和 lock 文件一致，缺什么补什么。

第七步：把项目交给别人。 只给代码，不给 .venv（依赖占了体积的绝大部分，而且换机器/换系统就不可用）。对方拿到代码、装好 uv 之后，在项目目录里：

uv 读 pyproject.toml 与 uv.lock，把该有的依赖一次装齐，并把 .venv 建好；然后同样 uv run main.py 就能跑。

第八步：日常维护命令。

命令 用途
uv add <包> 装依赖并写入 pyproject.toml
uv remove <包> 卸载并从 pyproject.toml 移除
uv sync 按 lock 文件还原环境
uv tree 查看依赖树
uv run <脚本> 在项目环境里执行
uv python install 3.12 装一个 Python 版本
uv python list 列出可用/已装的版本
uv python pin 3.12 把项目钉在某个版本
uv self update 升级 uv 自己
uv self uninstall 卸载 uv
uv tool install ruff 装命令行工具（不装进项目）

3. 关键概念与术语表

术语 含义
uv Astral 出的 Rust 实现 Python 包/环境管理器，一个二进制包办装包、建环境、管版本
pyproject.toml Python 标准项目描述文件（PEP 621），记录项目名、版本、requires-python、顶层依赖
uv.lock uv 的锁文件，记录完整依赖图、精确版本、下载源与哈希，用来复现环境
.python-version 一行文本，写明本项目使用的 Python 版本，uv 与 pyenv 都认
.venv 虚拟环境目录，含独立解释器与 site-packages；不提交、不打包
索引源 / 镜像站 pip 与 uv 下载包的仓库；国内镜像（清华、阿里云、南京大学等）是同一批包的镜像
UV_DEFAULT_INDEX 环境变量，指定默认索引源；也可在 pyproject.toml 里用 [[tool.uv.index]] 固定
依赖解析（resolution） 根据版本约束算出整张依赖图该用哪些版本的过程，是包管理器最耗 CPU 的部分
传递依赖 / 子依赖 你装的包自己所依赖的包，你不直接声明但要跟着装
uv add 装依赖并写回 pyproject.toml，同时更新 uv.lock
uv sync 按 pyproject.toml + uv.lock 还原环境，可理解为 Python 界的 npm install
uv run 用项目虚拟环境的解释器执行命令/脚本，替代「先 activate 再 python」
uv tool install 把命令行工具装到隔离环境并放进 PATH，例如 ruff、httpie
requires-python pyproject.toml 字段，声明项目支持的 Python 版本范围

4. 关键引用

「它属于新一代的 Python 环境管理工具。」——00:11

这句话定下了 uv 的定位：不是 pip 的补丁，而是把「环境」和「包」放在一起管的新一层。

「这个依赖计算是 UV……非常明显的比这个 PIP 要快的地方。」——01:03–01:06

快的第一个来源是解析器。装一个包要先算清整张依赖图取哪些版本，pip 在这里历史包袱最重。

「而我们的 UV 呢……它会同时去下载多个依赖。」——01:21

第二个来源是并发下载。单个包的下载速度未必更快，但同时发多个请求，总等待时间被压下来了。

「这个文件比较重要。」——07:25

说的是 pyproject.toml。项目的名字、版本、说明、Python 版本要求、你直接要的依赖，全在这里；后面的 uv sync、uv run 都围着它转。

「因为虚拟环境目录里边只是依赖。」——19:37

这是「把 .venv 排除在交付物之外」的理由：那个目录里没有一行你自己的代码，全是能从 lock 文件重装出来的第三方包。

「所以说从效率的角度来说呢……我们应该只把我们自己写的这个代码……传给需要我们代码的人。」——18:38–18:40

交付的边界由此确定：代码 + pyproject.toml + uv.lock 就够，环境靠 uv sync 现场重建。

「因为透彻，所以简单。」——23:44–23:45

作者自己的总结，也可以当作 uv 这类工具的设计取向：把复杂度留在工具内部，把命令表面压到最短。

5. 批判性分析

它真正解决的问题被低估了。 表面看 uv 是「更快的 pip」，但真正的收益是可复现：uv.lock 把子依赖的精确版本和哈希都钉死，换机器、进 CI、回滚线上版本时，装出来的东西是一致的。pip 用户要额外配 pip-tools 或 requirements.txt --hash 才能达到同一水平。

「快」有条件。 并行下载和缓存命中都依赖网络与磁盘布局。在 Windows 上如果缓存目录和项目目录不在同一个分区，uv 会退化成完整复制并提示 Failed to hardlink files; falling back to full copy，这时可以设 UV_LINK_MODE=copy 消掉警告，但磁盘占用会上去。第一次装包（缓存全空）也快不到哪去。

它没有替你解决所有问题。 教程覆盖的是单项目、单机、纯本地开发的主干路径。以下场景需要额外功课：多包仓库（workspace）、私有源认证、需要编译的 C 扩展（缺 MSVC Build Tools 时照样失败）、以及 Docker 镜像里的分层缓存（要把 pyproject.toml/uv.lock 单独先 COPY 再 uv sync，否则每次改代码都重装依赖）。

默认行为会「偷偷写文件」。 用环境变量设了默认源之后，uv add 会把这条源以 [[tool.uv.index]] 的形式写进 pyproject.toml（default = true）。好处是换机器不丢配置，坏处是同一个文件里一旦出现两个 [tool.uv.index] 表头，TOML 解析会直接报 Cannot declare ('tool', 'uv', 'index') twice —— 要么只留一条，要么用具名索引 [[tool.uv.index]] name = "..." 然后配合 tool.uv.sources 指定某个包走哪个源。

版本差异要自己核对。 老版本 uv init 会顺手 git init 并生成 .gitignore；0.13.8 的 uv init --no-package 只生成四个文件，既不建仓库也没有 .gitignore。教程里截图与现在跑出来的结果不一致，多半是版本差，不是操作错 —— 先 uv --version 再对照文档。

生态位置的变化值得注意。 uv 出自 Astral，同一家还做了 ruff（lint/格式化）和 ty（类型检查）。三个工具拼起来，正好覆盖「装依赖 — 检查格式 — 检查类型」这条日常链路，而它们的共同卖点都是「用 Rust 重写、快一个量级」。这不是巧合，而是 Python 工具链正在整体换代的一个切面。

6. 个人思考与应用

迁移既有项目。 手里有 requirements.txt 的项目不必推倒重来：uv add -r requirements.txt 会把清单里的包一次性加进 pyproject.toml 并生成 uv.lock，之后再也不用维护两份清单。只做一次性安装、不想改项目结构时，uv pip install -r requirements.txt 也能用，它兼容 pip 的语义。

CI 与部署用 uv sync --frozen。 --frozen 表示「不许改 lock 文件」，lock 和 pyproject.toml 不一致时直接失败，正好把「本地随手改了依赖但忘记锁」挡在流水线外。Docker 里则是先 COPY pyproject.toml uv.lock ./ 再 uv sync --frozen --no-dev，最后才 COPY . .，这样改业务代码不会让依赖层缓存失效。

镜像配在哪。 个人机器设 UV_DEFAULT_INDEX 环境变量最省事；团队项目更推荐写进 pyproject.toml 的 [[tool.uv.index]]，让源跟代码一起走、可 review、可回滚。代价是要接受「项目文件里出现基础设施信息」这件事。

别把 .venv 交出去，也别提交它。 交付物是「代码 + pyproject.toml + uv.lock」三件套。同理，.gitignore 里要有 .venv/，否则仓库体积会莫名其妙涨到几十兆。

Python 版本也钉住。 .python-version 写上 3.12，配合 uv python install 3.12，可以让「我这儿能跑、你那儿报语法错」这类问题少一大半 —— 解释器版本不一致导致的语法/标准库差异，比依赖版本差异更难查。

工具与依赖的边界。 ruff 这类「我要在命令行用、但不属于项目运行依赖」的工具，用 uv tool install ruff 装成全局命令；只有真正参与构建/测试的（比如 pytest）才 uv add --dev pytest 进 dependency-groups.dev。

和上一篇的关系。 如果已经写过 uv + ruff + ty 的完整工具链，这篇可以当成「uv 那一部分的最小可用版本」：它不涉及 lint 规则集、类型标注写法，只把「装、建、加、跑、交」这条主干走一遍。
