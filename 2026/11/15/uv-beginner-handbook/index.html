uv 入门：从装好到把项目交出去

文章发布时间:
2026-11-15

参考：B 站《新手必看！Python 包管理神器 UV》（UP：井水）。下面按真正动手的顺序走一遍：装 uv → 配国内镜像 → 初始化项目 → 建虚拟环境 → 装第一个依赖 → 运行 → 把项目交给别人 → 其余常用命令。文中命令与输出都在 uv 0.13.8 / Windows 上复核过，和早期版本有出入的地方单独标了出来。

1. 概述

uv 是一个用 Rust 写的 Python 环境与包管理工具。它把过去分散在 pip、virtualenv、pyenv、pip-tools 甚至 poetry 手里的活收进同一套命令：装依赖、锁版本、建虚拟环境、管理多个 Python 解释器、跑脚本，全部以 uv 开头。

对刚上手的人来说，最直接的价值不是「快」，而是少装几个工具、少记几套命令：

  • 装包不用先 python -m venv、再 activate、再 pip install；
  • 换 Python 版本不用去官网下安装包、改 PATH，uv python install 3.12 一句搞定；
  • 换电脑或交给同事，只要有 pyproject.toml 和 uv.lock，一条 uv sync 就能把环境还原得几乎一样。

快的来源可以拆成四条：

  1. 依赖解析更快。装一个库时，包管理器要先算出它连同子依赖的整张图该取哪些版本。pip 的解析器历史包袱重、重复计算多；uv 换成更高效的求解器，一次把整张图算完。
  2. 下载是并行的。pip 默认一个包装完再装下一个，uv 同时发多个下载请求，网络往返的等待被叠在一起。
  3. 缓存与硬链接。每个包版本的 wheel 存进全局缓存，装进项目时优先硬链接，同一份字节不重复落盘，第二次装几乎不花下载和磁盘时间。
  4. 没有解释器启动开销。整个工具是编译好的原生二进制，不像 Python 写的工具那样每次都先解释再执行。

需要先说清的边界：uv 没有定义新格式，它照样读 pyproject.toml、照样产出标准 wheel、照样建 venv 结构的目录。它改变的是工作流——依赖写回 pyproject.toml、虚拟环境由工具代管、版本和锁文件成为项目的正式组成部分。习惯 pip 的人最初会觉得「它怎么自己改了文件」，这正是设计意图。

2. 结构拆解

2.1 一个项目里有什么

在空目录里 uv init --no-package --python 3.13，会生成四个文件：

文件 作用 提交到 Git
pyproject.toml 项目身份证 + 你直接声明的依赖 要
uv.lock 完整依赖图：子依赖、精确版本、下载源、sha256 要
.python-version 这个项目的 Python 版本，内容就一行，如 3.13 要
main.py 入口脚本，uv init 生成，可改可删 要
README.md 项目说明，别人怎么用 要
.venv/ 虚拟环境本体，装好的包都落在这里 不要
.gitignore 哪些文件不进版本库 要（若生成）

uv.lock 是 uv add 时自动生成的，不是手动维护的文件。它开头写着 version = 1、revision = 5、requires-python = ">=3.13"，之后每个包一节，带 source（从哪个索引站下载）、sdist、wheels 和 sha256——所以同一份 lock 文件在任何机器上装出来的东西是逐字节可核对的。

pyproject.toml 是「结论」，uv.lock 是「证据」：前者只记你亲自要的顶层依赖，后者连子依赖一起钉死。类比前端就是 package.json 与 package-lock.json。

两种初始化布局要分清：

  • uv init --no-package：平铺项目，只有上面四五个文件，适合写脚本、跑练习；
  • uv init（默认）：可打包布局，多出 src/<项目名>/ 目录和构建配置，适合要发布成库的项目。不带 --python 时 uv 会挑本机可用的最新解释器，可能直接给出 requires-python = ">=3.15" 这种前沿版本，想要稳定就显式指定。

2.2 命令地图

阶段 命令 作用
装工具 pip install uv 用已有 Python 装 uv（官方也提供独立安装脚本）
配源 环境变量 UV_DEFAULT_INDEX 或 [[tool.uv.index]] 指定国内镜像，加速下载
建项目 uv init --no-package 生成 pyproject.toml 等项目骨架
建环境 uv venv 在项目内建 .venv（新版 uv add 也会自动建）
装依赖 uv add requests 解析、下载、安装、写回 pyproject.toml、更新 uv.lock
看结构 uv tree 打印依赖树，区分直接依赖与子依赖
运行 uv run main.py 用项目环境的解释器执行，免 activate
还原 uv sync 按 lock 重建环境，Python 界的 npm install
换版本 uv python install / list / pin 装、列、钉 Python 版本
自维护 uv self update / uv self uninstall 升级或卸载 uv 自身
命令行工具 uv tool install ruff 装到隔离环境并放进 PATH，不进项目依赖

2.3 五步走通

第一步，装 uv。 电脑上已经有 Python 的话，最简单是 pip install uv，然后 uv --version 确认。若终端还不认识 uv，关掉重开一个命令行窗口——PATH 的改动对已开的进程无效。

第二步，配国内镜像。 不改源的话，解析完仍要去国外站下载。最省事是设环境变量 UV_DEFAULT_INDEX，值填镜像地址（如清华源 https://pypi.tuna.tsinghua.edu.cn/simple）。Windows 上走「此电脑 → 属性 → 高级系统设置 → 环境变量 → 新建」，值的引号要去掉，改完重开终端。注意镜像只影响下载，不影响解析出的版本语义——但不同镜像的同步延迟会带来「今天锁的这个版本明天在源上没了」的偶发问题，这是镜像的固有代价。

2.4 把项目交出去

交付物只有三样：代码 + pyproject.toml + uv.lock，.venv 不交。

原因很实际：一次实测里项目目录总共 1.88 MB，其中 .venv 占 1.84 MB，自己写的代码只有 0.04 MB——环境占了 98%。而且 .venv 里是硬链接/复制出来的平台相关二进制，换系统、换 Python 版本都不可用，交出去只会变成对方的垃圾。

3. 关键概念与术语表

术语 含义
uv Astral 出的 Rust 实现 Python 包/环境管理器，一个二进制包办装包、建环境、管版本
pyproject.toml Python 标准项目描述文件（PEP 621），记录项目名、版本、requires-python、顶层依赖
uv.lock uv 的锁文件，记录完整依赖图、精确版本、下载源与哈希，用于复现环境
.python-version 一行文本，写明本项目使用的 Python 版本，uv 与 pyenv 都认
.venv 虚拟环境目录，含独立解释器与 site-packages；不提交、不打包
索引源 / 镜像站 pip 与 uv 下载包的仓库；国内镜像（清华、阿里云、南大等）是同一批包的副本
UV_DEFAULT_INDEX 环境变量，指定默认索引源；也可在 pyproject.toml 里用 [[tool.uv.index]] 固定
依赖解析（resolution） 根据版本约束算出整张依赖图该用哪些版本，包管理器最耗 CPU 的环节
传递依赖 / 子依赖 你装的包自己所依赖的包，不直接声明但要跟着装
uv add 装依赖并写回 pyproject.toml，同时更新 uv.lock
uv sync 按 pyproject.toml + uv.lock 还原环境，即 Python 界的 npm install
uv run 用项目虚拟环境的解释器执行命令或脚本，替代「先 activate 再 python」
uv tool install 把命令行工具装进隔离环境并放进 PATH，例如 ruff、httpie
requires-python pyproject.toml 字段，声明项目支持的 Python 版本范围（如 >=3.13）

4. 关键引用

「它属于新一代的 Python 环境管理工具。」——00:11

定位很清楚：不是 pip 的补丁，而是把「环境」和「包」放在一起管的新一层。

「这个依赖计算是 UV……非常明显的比这个 PIP 要快的地方。」——01:03–01:06

快的第一个来源是解析器。装一个包要先算清整张依赖图取哪些版本，pip 在这里包袱最重。

「而我们的 UV 呢……它会同时去下载多个依赖。」——01:21

第二个来源是并发下载。单个包的速度未必更快，但同时发多个请求，总等待时间被压下来。

「这个文件比较重要。」——07:25

说的是 pyproject.toml。项目名、版本、说明、Python 版本要求、你直接要的依赖都在这里，后面的 uv sync、uv run 都围着它转。

「因为虚拟环境目录里边只是依赖。」——19:37

这是「.venv 不进交付物」的理由：那个目录里没有一行你自己的代码，全是能从 lock 重装出来的第三方包。

「所以说从效率的角度来说呢……我们应该只把我们自己写的这个代码……传给需要我们代码的人。」——18:38–18:44

交付边界由此确定：代码 + 两个清单文件足够，环境靠 uv sync 现场重建。

「因为透彻，所以简单。」——23:44–23:46

作者的自我总结，也是这类工具的设计取向：把复杂度留在内部，把命令表面压到最短。

5. 批判性分析

它真正解决的问题被「快」这个词盖住了。 uv 的卖点听起来是速度，实际收益最大的是可复现：uv.lock 把子依赖的精确版本、下载源和哈希都钉死，换机器、进 CI、回滚线上版本时装出来的是同一套东西。pip 用户要额外上 pip-tools 或手写 --hash 才能到同一水平。

「快」是有条件的。 并行下载和硬链接都依赖网络与磁盘布局。Windows 上缓存目录与项目目录不在同一分区时，uv 会退化成完整复制并提示 Failed to hardlink files; falling back to full copy，这时设 UV_LINK_MODE=copy 只是消掉警告，磁盘占用照样上去。第一次装包（缓存全空）也没有快一个量级——快的是第二次。

它没有替你解决所有问题。 主线覆盖的是单项目、单机、纯本地开发。多包仓库（workspace）、私有源认证、需要编译的 C 扩展（缺 MSVC Build Tools 照样失败）、Docker 分层缓存，都需要额外功课。

默认行为会「偷偷写文件」。 用环境变量设了默认源之后，uv add 会把这条源以 [[tool.uv.index]] 写进 pyproject.toml；若文件里已存在同名表头，TOML 解析会直接报 Cannot declare ('tool', 'uv', 'index') twice。要么只留一条，要么用具名索引 [[tool.uv.index]] name = "..." 配合 [tool.uv.sources] 指定某个包走哪个源。

版本差异要自己核对。 较老的 uv 在 uv init 时会顺手 git init 并生成 .gitignore；0.13.8 的 uv init --no-package 只给四个文件，既不建仓库也没有 .gitignore。截图和本机结果不一致时，先 uv --version，再对照文档——多数是版本差，不是操作错。

生态位置值得注意。 uv 出自 Astral，同一家还做了 ruff（lint/格式化）和 ty（类型检查）。三者拼起来覆盖「装依赖—查格式—查类型」的日常链路，共同卖点都是「Rust 重写、快一个量级」。这不是巧合，而是 Python 工具链整体换代的一个切面。

6. 个人思考与应用

迁移既有项目。 手上有 requirements.txt 不必推倒重来：uv add -r requirements.txt 会把清单里的包一次加进 pyproject.toml 并生成 uv.lock。只做一次性安装、不想动项目结构时，uv pip install -r requirements.txt 也可用，它保留 pip 语义。

CI 与部署用 uv sync --frozen。 --frozen 表示「不许改 lock」，lock 与 pyproject.toml 不一致时直接失败，正好把「本地随手加了依赖但忘记锁」挡在流水线外。Docker 里则是先 COPY pyproject.toml uv.lock ./ 再 uv sync --frozen --no-dev，最后才 COPY . .，这样改业务代码不会让依赖层缓存失效。

镜像配在哪。 个人机器设 UV_DEFAULT_INDEX 最省事；团队项目更推荐写进 pyproject.toml 的 [[tool.uv.index]]，让源跟代码一起走、可 review、可回滚，代价是项目文件里混进了基础设施信息。

Python 版本也钉住。 uv python pin 3.12 会把 .python-version 写成 3.12；配合 uv python install 3.12，「我这儿能跑、你那儿报语法错」这类问题能少一大半——解释器版本导致的语法/标准库差异，比依赖版本差异更难查。

工具与依赖分开放。 ruff 这类「只在命令行用、不属于运行依赖」的工具，用 uv tool install ruff 装成全局命令；真正参与构建/测试的（如 pytest）才 uv add --dev pytest，进 dependency-groups.dev。

别提交 .venv。 交付物是「代码 + pyproject.toml + uv.lock」三件套；.gitignore 里必须有 .venv/，否则仓库体积会莫名其妙涨到几十兆，而且历史里删不干净。

什么时候还不该换。 项目已经用 poetry 且团队熟手、CI 镜像里 pip 缓存调得很顺、或者依赖里有只能在特定环境编译的包时，迁移的收益小于风险。uv 的兼容模式（uv pip）可以先只换「装」这一环，跑顺了再动 lock 与项目文件。
