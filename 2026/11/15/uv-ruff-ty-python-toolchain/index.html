uv + ruff + ty：一套现代 Python 工具链

文章发布时间:
2026-11-15

参考视频：《现代 Python 工具链：uv、ruff、ty》。

一句话：uv 管环境与依赖，ruff 管格式与 lint，ty 管类型 —— 三个 Rust 工具拼起来，替掉 pip + venv + flake8 + isort + black + mypy 那一整排，让 Python 项目的初始化、装包、检查都快到不用等。

引言

搭一个像样的 Python 项目，通常得拼七八个工具：pip 装包、venv 建环境、pip-tools 锁版本、flake8 查问题、isort 排 import、black 管格式、mypy 查类型。它们各有各的配置位置（setup.cfg、.flake8、pyproject.toml），跑一遍要几十秒，慢到你会想着”下次再查吧”。

Astral 用三个 Rust 程序把这件事收了：

工具 负责 替代掉
uv 包与项目管理、虚拟环境、Python 版本 pip、venv、pip-tools、poetry 的一部分
ruff lint + 格式化（含 import 排序） flake8、isort、black、pyupgrade
ty 类型检查 + 语言服务器 mypy、Pyright、Pylance

三者同属 Astral，2026 年 3 月被 OpenAI 收购，工具承诺继续开源（MIT）。成熟度得分开说：uv 和 ruff 现在可以直接上，ty 还在 Beta（2025 年 12 月发布，至今仍是 0.0.x 版本号），建议先和 mypy 并行跑一段。

下文命令在 uv 0.13.8 上验证过；uv init 的默认布局在 uv 0.13 有过一次变化，1.2 节单独说明。

两个容易混的点：

  • pip install uv 这一步的下载走的是 pip 自己的镜像配置，和 uv 的索引无关。uv 的索引只影响 uv add / uv lock / uv sync 去哪找包。
  • 这条环境变量不必长期手动维护：uv init 之后第一次 uv add 时，uv 会把当前生效的默认索引写进 pyproject.toml（[[tool.uv.index]] 表，default = true）。项目一提交，换台机器不用再配环境变量也能复现。

1.2 初始化项目

产物是 .python-version、pyproject.toml、main.py、README.md（0.11 还带一个 .gitignore）。

布局在 0.13 变过：uv 0.13 起 uv init 默认生成「可打包项目」——src/<包名>/__init__.py、[project.scripts] 入口、uv_build 构建后端，没有平铺的 main.py。想要简单项目就加 --no-package。

pyproject.toml 里关键一行是兼容范围：

它和 .python-version 里写的 3.13（本机跑哪个解释器）分工不同：前者是「这个项目声明支持哪些版本」，后者是「我用哪个版本跑」。想连小版本一起锁死，把 requires-python 改成 ==3.13.*。如果 .python-version 里的版本本机没有，uv 会自己下（uv python install 3.13 可预装，uv python list 看已有的）。

1.3 虚拟环境：不用自己建

uv add、uv run、uv sync 发现没有 .venv 都会自己建，实测 uv sync 直接输出 Creating virtual environment at: .venv。

手动 uv venv 只在两种场合需要：想指定解释器（uv venv --python 3.12），或想指定别的目录。

平时也不用 activate——uv run main.py 会自动用项目环境、必要时先同步依赖再跑。只有要进交互式 REPL、或让 GUI 调试器挂上去时，才需要激活：

日常就这几条：

几个值得记住的细节：

  • uv.lock 要提交进 git。它是跨平台的通用锁文件（不是只锁当前机器），记录了每个包的 hash。
  • CI 用 uv sync --frozen：只按锁装、不尝试更新锁；锁和 pyproject.toml 对不上时直接失败，避免线上悄悄换版本。
  • 升级是单独的动作：uv lock --upgrade（全升）或 uv lock --upgrade-package numpy（单升）。
  • uv add 默认写兼容范围（numpy>=2.5.0），精确版本记录在 uv.lock 里——这正是它比 pip install 稳的地方。

1.5 专用索引：PyTorch 为什么装成 CUDA 版

uv add torch 装完常常是几个 G 的 CUDA 包，哪怕机器上根本没有显卡。原因是 PyPI 上 torch 的默认 wheel 带 CUDA，CPU 版轮子只发布在 PyTorch 自己的索引里。所以要告诉 uv「torch 去那个源找」：

三个字段看懂就不会乱改：

  • default = true：这条是默认索引，等价于把 UV_DEFAULT_INDEX 写进项目。
  • explicit = true：这条索引只给显式点名它的包用，不会拿去解析别的包——防止 PyTorch 镜像里的同名包污染正常解析。
  • [tool.uv.sources]：把 torch 钉到 pytorch-cpu 这条索引上。

两个索引必须写成数组表 [[tool.uv.index]]。写成两段同名的 [tool.uv.index] 表头，TOML 不允许同名表重复定义，会得到 Cannot declare ('tool', 'uv', 'index') twice，整个 pyproject.toml 解析失败（用 Python 的 tomllib 和 uv 都能复现）。

二、ruff：格式化与 lint

2.1 编辑器里的两个动作

装进开发依赖：uv add --dev ruff。VS Code 里搜 ruff，装 Astral 官方那个扩展（ID charliermarsh.ruff）。

装好之后日常只用两个动作：

  1. 编辑器里右键 → 「格式化文档」：格式化代码，等价 ruff format。
  2. Ctrl+Shift+P → Ruff: Format imports：整理 import（等价 isort），标准库自动排到最前面。

顺带把概念分清：lint 是「静态检查」——不运行代码，只读源码找可疑写法（没用到的变量、未定义的引用、可变默认参数、过时语法……），报 warning/error；format 只管长什么样（缩进、换行、引号）。所以动词是「跑一遍 lint」，不是「lint 一下格式」。

一个必须知道的副作用：装 ty 扩展后，它会默认把 python.languageServer 设为 "None"，主动接管 Pylance 的位置（避免两个语言服务器打架）。如果你还想留着 Pylance 的补全和悬停提示、只用 ty 做检查，得手动把这个设置改回去。

3.2 一个报错长什么样

典型例子：

ty 立刻在编辑器里标红，报错原文：

Function always implicitly returns None, which is not assignable to return type str

info: Consider changing the return annotation to -> None or adding a return statement

这段其实藏了两个错误：函数声明返回 str 但实际没有 return（永远返回 None）；调用 main() 时又漏传了 name 参数。ty 两个都会指出。

3.3 现在能不能用

ty 是 Astral 对标 mypy / Pyright / Pylance 的产品，但仍在 Beta（2025 年 12 月发布，至今 0.0.x）。它已经能覆盖日常用法，规则覆盖率还在补。稳妥的过渡方式：CI 里先只对新增代码卡 ty check，和 mypy 并行跑一两个月，再决定要不要完全替换。
