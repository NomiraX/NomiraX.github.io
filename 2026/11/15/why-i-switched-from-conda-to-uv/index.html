从 Conda 换到 uv：让一个环境只属于一个项目

文章发布时间:
2026-11-15

这是一篇视频笔记（原视频：BV19Nbq6vEq9《我为什么弃用 Conda，改用 uv 来管理 Python 虚拟环境》）。不是逐字抄录：视频里几处与当前 uv 实际行为不符的地方我按官方文档改掉了，几处省略但会真正影响你上手的东西补了进来。

一、想换掉 Conda 的真实理由

不是因为 Conda 慢，而是因为它把环境放在了一个和项目无关的地方。

  • 环境要起名字。 conda create -n xxx，而名字是全局的、语义很弱的：env_a、env_old、env_debug、env_test、env_backup。起名是玄学，过了半年这些名字一个都记不起来是干什么的。
  • 新环境装包要从头来一遍。 即使同一个包在别的环境里已经装过，新环境里还是得重新解析、重新下载、重新落盘。
  • 几十个项目、十几个环境，对应关系全靠记忆。 环境躺在 ~/miniconda3/envs/ 下，项目躺在另一个盘的另一层目录里，中间没有任何东西把两者绑在一起。每次都得先 conda activate 才想得起要激活哪个。
  • requirements.txt 不是锁。 手写的多半只有 >=；pip freeze 出来的虽然带 ==，但它记录的是“我这台机器上装成了什么”，不是“这个项目需要什么”，里面混着传递依赖、平台相关的可选包，换台机器仍然可能装出不一样的东西。
  • 开源项目已经在用它了。 现在不少新项目（比如 IndexTTS2）的依赖管理就是 uv，不熟悉的话连跑起来都要先猜。

我想换来的东西只有一句话：环境跟着项目走。

进到项目目录，就知道这个环境是什么、用什么 Python、装了哪些包、锁在哪个版本——不需要名字，不需要记忆，不需要激活。

二、uv 是什么

Rust 写的包管理与项目管理工具，Astral 出品（和 ruff 是同一家）。官方口径是比 pip 快 10–100 倍，但速度只是副产品；它真正省事的地方是把四件原本分散的事收进了一个二进制：

  • Python 解释器本身（uv python，替代 pyenv）
  • 虚拟环境（uv venv，替代 venv / virtualenv）
  • 依赖与锁文件（uv add / uv lock / uv sync，替代 pip + pip-tools）
  • 命令行工具（uv tool / uvx，替代 pipx）

以及一层兼容层 uv pip，让所有老习惯和 requirements.txt 都还能用。

三、最短的一条上手路径

这里的 uv run 就是全部的“激活”：不需要 conda activate，不需要 source .venv/bin/activate，命令前面加 uv run 就行。

补正 1：uv init 不加参数，现在不生成 main.py

视频里说“不加 --bare 会给你一个 main.py 入口文件”。这是旧版本的行为。v0.12 之后，uv init 默认创建的是“可打包的应用”：

并且在 pyproject.toml 里注册 [project.scripts]，用 uv run <项目名> 执行。想要 main.py 得显式加 --no-package；只想要一个 pyproject.toml 用 --bare。

在已有代码的目录里初始化，--bare 几乎总是更顺手，因为它不会给你造 src/、不会覆盖你已有的东西。区别记一句就够：--bare 只给 pyproject.toml，--no-package 给 pyproject.toml + main.py，什么都不加给一个完整的打包项目。

补正 2：uv python pin 不是 requires-python

视频里 uv python pin 3.12，紧接着 pyproject.toml 里写着 requires-python = “>=3.13”。看上去像自相矛盾，其实不是——这两个东西管的是两件事：

  • .python-version（由 uv python pin 写）：优先用哪个解释器。软偏好。
  • requires-python（pyproject.toml 里）：这个项目支持哪些 Python。硬约束。

uv python pin 只改后者之外的那个文件，不会去动 requires-python。如果 pin 的版本不满足 requires-python，uv 会拒绝使用它。所以“在 uv 里可以随时升降 Python 版本”这句话要补一个条件：先改 requires-python，再重新 uv lock，环境才会真的换解释器——uv 不会为了迁就你的 pin 而破坏项目的兼容性声明。

四、三个文件和一个目录

这套东西之所以“看得见”，是因为它能用一个目录树讲清楚。

文件 谁维护 里面是什么 进 git
pyproject.toml 人（或 uv add） 项目元数据 + 宽泛依赖 fastapi>=0.115 + requires-python 进
uv.lock uv 自动 精确版本 + 哈希 + 跨平台 marker 必须进
.python-version uv python pin 首选解释器版本 建议进
.venv/ uv sync / uv run 装好的包，一次性产物 不进

pyproject.toml 和 uv.lock 的分工，是整套设计里最值得记住的一件事：

人写“需求”，机器写“解”。

pyproject.toml 里只会出现你直接用的那几个包，以及它们的宽泛版本范围；uv.lock 里是解析出来的完整闭包——fastapi 会牵出 pydantic>=2.13.4、starlette、anyio 等等，每个都带版本、下载地址和哈希，而且对不同平台/不同 Python 版本分别记录（这就是“universal lockfile”的含义）。

requirements.txt 时代的问题是这两件事混在一个文件里，所以才会出现“你装得上、我装不上”。uv.lock 是自动生成的、不该手改，但它必须提交——提交它，等于把“一定能装出来的那个解”一起提交了。

五、uv run：根本不需要激活

uv run 在每次执行前都会核对两件事：lock 是否与 pyproject.toml 一致，环境是否与 lock 一致；不一致就先同步，然后才跑。所以“要不要先 uv sync”这个问题，答案是不用。

需要 shell 里连续敲很多命令时，激活 .venv 仍然可以：Windows 下 .venv\Scripts\activate（PowerShell 用 Activate.ps1），Unix 下 source .venv/bin/activate。但这是可选路径，不是必经步骤。

六、sync / lock 的三种严格程度

这是生产中真正会用到的一层，视频没展开：

--locked 和 --frozen 的区别值得单独记：前者是“检查后拒绝”，后者是“压根不检查”。CI 里用 --locked，你能立刻知道有人改了 pyproject.toml 却忘了提交 lock；只在要复现一份历史状态时用 --frozen。

七、老项目和老环境怎么过渡

uv add 和 uv pip install 的区别是这里最容易踩的坑。 uv add 改的是“项目”：pyproject.toml + uv.lock + .venv 三处一起变。uv pip install 改的只是“当前这个 .venv”，uv.lock 一行都不会动——下次 uv sync 会把它当多余的包清掉。

顺便纠正一个常见说法：uv add -r requirements.txt 不是“原样把 requirements 里的东西装进来”，它是把里面的包当作直接依赖写进 pyproject.toml，然后重新解析。所以它会把 pip freeze 里那些传递依赖也提成顶层依赖——从 pip freeze 的清单迁过来时，先搬、再手工删掉明显的传递包，比一条条对着 import 捋更省事。

八、“不用重复装包”到底是怎么做到的

不是环境之间共享，而是全局缓存 + 链接。

uv 把下载和解包过的 wheel 放在一个全局缓存里（uv cache dir 可以看到路径），往 .venv 里装的时候优先用硬链接/reflink 而不是复制文件。所以第二个环境“安装”一个已经缓存过的包，既不怎么花磁盘，也不怎么花时间——uv pip install numpy 在大包上秒完，就是这个原因。

有一个前提很容易被忽略：缓存目录必须和虚拟环境在同一个文件系统上，跨盘就只能退化成复制。Windows 上项目放在 D 盘、而缓存默认在 C:\Users\<你>\AppData\Local\uv\cache，就享受不到这个好处；把 UV_CACHE_DIR 指到项目所在那块盘，速度差别是能感觉到的。

九、uv 不管什么（这部分别指望它）

  • 不装非 Python 的运行时依赖。 CUDA toolkit、cuDNN、MKL、系统库（libgl、ffmpeg）、C/C++ 编译器，uv 一概不管。conda 能管，因为它管的是“二进制包”而不是“Python 包”。
  • 不能改解释器的构建变体。 uv 自己下载的 CPython 来自 python-build-standalone，是预编译的便携版；没有 python=3.11=mkl 这种带 BLAS 变体的说法。
  • 不解决驱动。 GPU 驱动、nvidia-smi 里能看到的那些，永远是操作系统的事。

所以正确的结论不是“conda 该扔了”，而是分层：

机器层（驱动、CUDA、系统库）交给系统包管理器或 conda；
项目层（哪个 Python、装哪些包、锁成什么版本）交给 uv。

两者并不冲突。conda 里建好的环境，用 uv pip install --python <那个环境的 python> 一样能享受 uv 的解析速度。只是更常见的组合是：用 uv 管项目，GPU 那层直接吃系统驱动，连 conda 都不需要。

真要装 CUDA 版 PyTorch，uv 的正确姿势是在 pyproject.toml 里声明 index，而不是在命令行背一长串 --index-url：

explicit = true 的意思是：这个 index 只给明确指过去的包用。否则一旦它被当成候选源，jinja2 这类通用包也可能从 PyTorch 的索引里被拉走，解析结果会变得莫名其妙。

十、从 conda 迁过来，按这个顺序做

  1. 先存档，别删老环境：conda env export > environment.yml。
  2. 新目录 uv init --bare，uv python pin 到老环境的 Python 次版本（次版本，不是补丁版本）。
  3. 依赖只留顶层。先用 uv add -r 把全量搬进去，再 uv remove 掉明显的传递依赖——传递依赖本来就该由 lock 决定，写进 pyproject.toml 反而会把它钉死。
  4. uv lock，然后跑测试。之前“能跑但现在装不上”的包，通常在这一步暴露：有的包没有 wheel 只能源码编译（这就需要系统里有编译器，属于第九节说的那一层）。
  5. 提交 pyproject.toml + uv.lock；.venv 别提交。

十一、几个容易踩的坑

  • 镜像：uv 不读 pip.conf / pip.ini，要单独配。UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple，或命令上 uv lock --default-index ...。
  • 只提交 lock 不提交 pyproject.toml 是无效的：uv 要用 pyproject.toml 判断 lock 是否过期。
  • uv pip install 装的东西会消失：下次 uv sync 会把它当多余的包清掉。一次性依赖用 uv run --with。
  • requires-python 写太窄：写成 ==3.12.* 会让协作者和 CI 都装不了别的版本，一般 >=3.12 就够。
  • 在已有 pyproject.toml 的目录里 uv init 会直接报错退出——不会覆盖，这点是安全的，但也意味着它不会帮你“补全”已有文件，得手改。

最后

两句话。

第一，现在判断一个 Python 项目靠不靠谱，有没有 uv.lock 已经比 README 里写了什么更可靠——它说明作者真的在意别人能不能跑起来。

第二，命令不用背。只要记住 pyproject.toml 是人写的需求、uv.lock 是机器写的解、.venv 是一次性产物，剩下三件事（加依赖、跑命令、升级）想不起来的时候去查文档就行。真正需要理解的不是命令，是这三者的分工。
