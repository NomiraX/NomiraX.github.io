现代python工具链：uv&ruff

文章发布时间:
2026-11-15

一个 Python 项目在根部其实只有两件事要管：跑得起来（哪个解释器、装哪些包、锁成什么版本）和写得像样（导入顺序、无用变量、风格统一）。前者是 uv，后者是 ruff。两个工具同出自 Astral、都用 Rust 写成单个可执行文件、都从同一份 pyproject.toml 读配置，所以它们天然是一套，而不是两个孤立的选择。

整理自两期 B 站视频：《我为什么弃用 Conda，改用 uv 来管理 Python 虚拟环境》 与 《Ruff 使用指南：最新的超快速代码格式化工具》。

以前维护一个 Python 项目，根部要摆四套东西：

  • requirements.txt + venv 管依赖，但 requirements.txt 不是锁；
  • pyenv 管解释器版本；
  • flake8 + 一堆插件管检查，每个插件都有自己的配置节；
  • black + isort 管格式，两者风格还不一定一致。

这四套各自演化，配置文件互相不知道对方在说什么。换台机器复现一遍，经常是“能跑，但不是原来那个样子”。

uv 把前两件吞掉，ruff 把后两件吞掉，而且两者共用 pyproject.toml。下面分两章讲，最后再说它们是怎么接上的。

uv：环境跟着项目走

Conda 的问题：环境不在项目里

不是因为 Conda 慢，而是因为它把环境放在了一个和项目无关的地方。

  • 环境要起名字。 conda create -n xxx，而名字是全局的、语义很弱的：env_a、env_old、env_debug、env_test、env_backup。起名是玄学，过了半年这些名字一个都记不起来是干什么的。
  • 新环境装包要从头来一遍。 即使同一个包在别的环境里已经装过，新环境里还是得重新解析、重新下载、重新落盘。
  • 几十个项目、十几个环境，对应关系全靠记忆。 环境躺在 ~/miniconda3/envs/ 下，项目躺在另一个盘的另一层目录里，中间没有任何东西把两者绑在一起。每次都得先 conda activate 才想得起要激活哪个。
  • requirements.txt 不是锁。 手写的多半只有 >=；pip freeze 出来的虽然带 ==，但它记录的是“我这台机器上装成了什么”，不是“这个项目需要什么”，里面混着传递依赖、平台相关的可选包，换台机器仍然可能装出不一样的东西。
  • 开源项目已经在用它了。 现在不少新项目（比如 IndexTTS2）的依赖管理就是 uv，不熟悉的话连跑起来都要先猜。

想换来的东西只有一句话：环境跟着项目走。

进到项目目录，就知道这个环境是什么、用什么 Python、装了哪些包、锁在哪个版本——不需要名字，不需要记忆，不需要激活。

uv 是什么

Rust 写的包管理与项目管理工具，Astral 出品（和 ruff 是同一家）。官方口径是比 pip 快 10–100 倍，但速度只是副产品；它真正省事的地方是把四件原本分散的事收进了一个二进制：

  • Python 解释器本身（uv python，替代 pyenv）
  • 虚拟环境（uv venv，替代 venv / virtualenv）
  • 依赖与锁文件（uv add / uv lock / uv sync，替代 pip + pip-tools）
  • 命令行工具（uv tool / uvx，替代 pipx）

以及一层兼容层 uv pip，让所有老习惯和 requirements.txt 都还能用。

最短的一条上手路径

这里的 uv run 就是全部的“激活”：不需要 conda activate，不需要 source .venv/bin/activate，命令前面加 uv run 就行。

在已有代码的目录里初始化，--bare 几乎总是更顺手，因为它不会给你造 src/、不会覆盖你已有的东西。区别记一句就够：--bare 只给 pyproject.toml，--no-package 给 pyproject.toml + main.py，什么都不加给一个完整的打包项目。

两处版本声明不是一回事

uv python pin 3.12 之后，pyproject.toml 里可能仍然写着 requires-python = ">=3.13"。看着像自相矛盾，其实是两层不同的东西：

  • .python-version（由 uv python pin 写）：优先用哪个解释器。软偏好。
  • requires-python（pyproject.toml 里）：这个项目支持哪些 Python。硬约束。

uv python pin 只写 .python-version，不会去动 requires-python。如果 pin 的版本不满足 requires-python，uv 会拒绝使用它。所以在 uv 里升降 Python 版本是有前提的：先改 requires-python，再重新 uv lock，环境才会真的换解释器——uv 不会为了迁就你的 pin 而破坏项目的兼容性声明。

顺带一提，这个 requires-python 后面还会被 ruff 用上，写到第二章时会再次遇到。

三个文件和一个目录

这套东西之所以一目了然，是因为它能用一个目录树讲清楚。

文件 谁维护 里面是什么 进 git
pyproject.toml 人（或 uv add） 项目元数据 + 宽泛依赖 fastapi>=0.115 + requires-python 进
uv.lock uv 自动 精确版本 + 哈希 + 跨平台 marker 必须进
.python-version uv python pin 首选解释器版本 建议进
.venv/ uv sync / uv run 装好的包，一次性产物 不进

pyproject.toml 和 uv.lock 的分工，是整套设计里最值得记住的一件事：

人写“需求”，机器写“解”。

pyproject.toml 里只会出现你直接用的那几个包，以及它们的宽泛版本范围；uv.lock 里是解析出来的完整闭包——fastapi 会牵出 pydantic>=2.13.4、starlette、anyio 等等，每个都带版本、下载地址和哈希，而且对不同平台/不同 Python 版本分别记录（这就是 universal lockfile 的含义）。

requirements.txt 时代的问题是这两件事混在一个文件里，所以才会出现“你装得上、我装不上”。uv.lock 是自动生成的、不该手改，但它必须提交——提交它，等于把一定能装出来的那个解一起提交了。

uv run：不需要激活

uv run 在每次执行前都会核对两件事：lock 是否与 pyproject.toml 一致，环境是否与 lock 一致；不一致就先同步，然后才跑。所以答案很直接：不用先手动 uv sync。

需要 shell 里连续敲很多命令时，激活 .venv 仍然可以：Windows 下 .venv\Scripts\activate（PowerShell 用 Activate.ps1），Unix 下 source .venv/bin/activate。但这是可选路径，不是必经步骤。

--locked 和 --frozen 的区别值得单独记：前者是“检查后拒绝”，后者是“压根不检查”。CI 里用 --locked，你能立刻知道有人改了 pyproject.toml 却忘了提交 lock；只在要复现一份历史状态时用 --frozen。

老项目与老环境怎么过渡

uv add 和 uv pip install 的区别是这里最容易踩的坑。 uv add 改的是“项目”：pyproject.toml + uv.lock + .venv 三处一起变。uv pip install 改的只是“当前这个 .venv”，uv.lock 一行都不会动——下次 uv sync 会把它当多余的包清掉。

一个常被误解的点：uv add -r requirements.txt 不是把 requirements 里的东西原样装进来，它是把里面的包当作直接依赖写进 pyproject.toml，然后重新解析。所以它会把 pip freeze 里那些传递依赖也提成顶层依赖——从 pip freeze 的清单迁过来时，先搬、再手工删掉明显的传递包，比一条条对着 import 捋更省事。

为什么换环境不用重新下载

不是环境之间共享，而是全局缓存 + 链接。

uv 把下载和解包过的 wheel 放在一个全局缓存里（uv cache dir 可以看到路径），往 .venv 里装的时候优先用硬链接/reflink 而不是复制文件。所以第二个环境“安装”一个已经缓存过的包，既不怎么花磁盘，也不怎么花时间——uv pip install numpy 在大包上秒完，就是这个原因。

有一个前提很容易被忽略：缓存目录必须和虚拟环境在同一个文件系统上，跨盘就只能退化成复制。Windows 上项目放在 D 盘、而缓存默认在 C:\Users\<你>\AppData\Local\uv\cache，就享受不到这个好处；把 UV_CACHE_DIR 指到项目所在那块盘，速度差别是能感觉到的。

uv 不管什么（这部分别指望它）

  • 不装非 Python 的运行时依赖。 CUDA toolkit、cuDNN、MKL、系统库（libgl、ffmpeg）、C/C++ 编译器，uv 一概不管。conda 能管，因为它管的是“二进制包”而不是“Python 包”。
  • 不能改解释器的构建变体。 uv 自己下载的 CPython 来自 python-build-standalone，是预编译的便携版；没有 python=3.11=mkl 这种带 BLAS 变体的说法。
  • 不解决驱动。 GPU 驱动、nvidia-smi 里能看到的那些，永远是操作系统的事。

所以结论不是“conda 该扔了”，而是分层：

机器层（驱动、CUDA、系统库）交给系统包管理器或 conda；
项目层（哪个 Python、装哪些包、锁成什么版本、代码怎么检查）交给 uv + ruff。

两者并不冲突。conda 里建好的环境，用 uv pip install --python <那个环境的 python> 一样能享受 uv 的解析速度。只是更常见的组合是：用 uv 管项目，GPU 那层直接吃系统驱动，连 conda 都不需要。

真要装 CUDA 版 PyTorch，uv 的正确姿势是在 pyproject.toml 里声明 index，而不是在命令行背一长串 --index-url：

explicit = true 的意思是：这个 index 只给明确指过去的包用。否则一旦它被当成候选源，jinja2 这类通用包也可能从 PyTorch 的索引里被拉走，解析结果会变得莫名其妙。

uv 这边的坑

  • 镜像：uv 不读 pip.conf / pip.ini，要单独配。UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple，或命令上 uv lock --default-index ...。
  • 只提交 lock 不提交 pyproject.toml 是无效的：uv 要用 pyproject.toml 判断 lock 是否过期。
  • uv pip install 装的东西会消失：下次 uv sync 会把它当多余的包清掉。一次性依赖用 uv run --with。
  • requires-python 写太窄：写成 ==3.12.* 会让协作者和 CI 都装不了别的版本，一般 >=3.12 就够。
  • 在已有 pyproject.toml 的目录里 uv init 会直接报错退出——不会覆盖，这点是安全的，但也意味着它不会帮你补全已有文件，得手改。

ruff：代码跟着标准走

ruff 是什么

同样是 Astral 出品、Rust 写的单个可执行文件。它把一整套工具吞进了一个命令：

过去 现在
flake8 + 几十个插件（bugbear、bandit、pyupgrade…） ruff check
isort（导入排序） ruff check（I 规则组）
black（格式化） ruff format
autoflake（删无用导入/变量） ruff check --fix

八百多条可选规则，覆盖从“未使用的导入”到“该用 pathlib 而不是 os.path”的各个层次。日常项目跑一遍是秒级——不是“比 flake8 快一点”，是快到可以塞进保存文件的那一刻。

它和 uv 的关系不只在出品方：配置就写在 pyproject.toml 里，和依赖声明做邻居。

装 ruff：三种粒度

uv tool 管的是全局工具：uv tool list 看装了哪些，uv tool upgrade ruff 升级，uv tool uninstall ruff 卸载。它相当于把 pipx 的活接了过来。

项目里用 uv add --dev ruff 更好，因为版本跟着 uv.lock 走——同事克隆下来 uv sync 就得到同一个 ruff。它在 pyproject.toml 里落在 [dependency-groups] dev 而不是 dependencies，不会被打进运行时依赖。

传统方式也不是不行：pip install ruff 只在当前虚拟环境可用；pipx install ruff 是隔离环境下的全局命令。但既然已经在用 uv，前两种没必要。

自动修复的两个档位

默认的 --fix 是保守的：它只应用那些不会改变程序语义的修复。--unsafe-fixes 才会动可能改变行为的（比如删掉一个看起来没用的赋值，而那个赋值右侧可能有副作用）。

不确定它会干什么的时候，先 --diff：输出和 git diff 一样，红的是要删的，绿的是要加的。

--statistics 在接手老项目时特别好用——一眼看出五千条警告里，是哪三条规则贡献了四千条。

格式化：ruff format

它和 black 是同一个风格家族，官方口径的兼容度在 99.9% 以上：同一个文件，两者格式化结果几乎一样，但 ruff 快了不止一个数量级。缩进、空行、引号、长行折行、magic trailing comma，这些都是它的活。

顺序很重要：先 ruff check --fix，再 ruff format。 反过来的话，自动修复可能又把格式弄乱，产生二次 diff。

ruff format 不管导入顺序（那是 I 规则的事），也不管未使用的变量（那是 linter 的事）。两个命令分工明确，别指望一个顶两个。

几个概念一次说清：

  • select 是整体替换默认规则集，extend-select 是在默认之上追加。日常用后者，不容易误伤。
  • 规则代码可以是组（PTH 代表 flake8-use-pathlib 全组），也可以精确到单条（T201）。
  • select = ["ALL"] 是另一种玩法：全开，然后用 ignore 一条条减。适合想彻底梳理一遍的项目——十行代码能报出十几条，是正常的。
  • per-file-ignores 是必需的逃生口。测试文件里的 assert（S101）、__init__.py 里的重导出（F401）、notebook 里的 print（T20），都该按目录关掉而不是全局关掉。

配置也可以放在 ruff.toml 或 .ruff.toml 里，语法相同、省掉 [tool.ruff] 前缀。多个文件同时存在时优先级是 .ruff.toml > ruff.toml > pyproject.toml；子目录里的配置会覆盖父目录的，需要继承就用 extend。

配套习惯：

  • 把 black、isort、flake8、autoflake 的扩展全卸了，留着会互相打架（同一个文件被两个格式化器轮流改）。
  • 编辑器用的 ruff 来自项目 .venv 时，才能保证和 CI 是同一个版本；这也是前面推荐 uv add --dev ruff 的原因。
  • 悬停能看到规则说明，点问题面板里的链接直接跳官方文档——这是上手规则体系最快的方式。

其它编辑器都是同一个思路：让 LSP 指向 ruff server。Neovim、Helix、Zed、PyCharm（2025.3 起内置）都有现成配置。

--output-format=github 会把问题变成 PR 里的行内注释；需要给别的系统消费就换 json、sarif、junit。

一个细节：pre-commit 里的 hook id 在过去叫 ruff，现在拆成了 ruff-check 和 ruff-format。老配置文件里那个 ruff 仍然能用，但只做检查不做格式化。

ruff 这边的坑

  • flake8 的配置不会自动搬过来。 setup.cfg 里的 [flake8] 段 ruff 不读，得手工翻译成 [tool.ruff.lint]。好在规则代码基本沿用，翻译量不大。
  • select = ["ALL"] 会一次性唤醒所有规则，包括文档字符串（D）、print（T20）、assert（S101）、魔法数（PLR2004）。上生产前一定配 per-file-ignores，否则测试目录会红成一片。
  • --fix 不等于“全部修好”。 剩下的要么不安全，要么需要人判断；--statistics 看还剩什么。
  • ruff format 和 black 的差异：极少数边界写法结果不同（比如长字符串拼接的折行），迁移时全量跑一遍再 review diff，别假设零差异。

最后

回到开头那两件事，现在能看清它们是怎么咬合的：

  • uv 保证“跑得起来且跑得一样”：解释器版本、依赖闭包、锁文件。
  • ruff 保证“写得一样”：同一套规则、同一个格式化结果。

咬合点在 pyproject.toml：[project]、[tool.uv]、[tool.ruff] 三节并排，一个文件读完整个项目的约定。

还有一条隐式的线：ruff 的 target-version 如果没显式写，会从 requires-python 推断。也就是说，你在 uv 那边声明“这个项目支持 Python 3.12+”，ruff 就自动不去建议只有 3.13 才有的语法。两个工具不需要你手工同步两次。

三句话收尾。

第一，环境这件事的判据已经变了：现在看一个 Python 项目靠不靠谱，有没有 uv.lock 比 README 里写了什么更可靠——它说明作者真的在意别人能不能跑起来。

第二，代码规范这件事的判据也变了：有没有 [tool.ruff] 配置，说明作者有没有把风格当约定而不是当个人偏好。

第三，命令不用背。记住 pyproject.toml 是人写的需求、uv.lock 是机器写的解、.venv 是一次性产物、[tool.ruff] 是团队共识——剩下的事查文档就行。真正需要理解的不是命令，是这几个东西各自负责什么。
