常用大模型 API 与消息结构

Created2026-11-15|Updated2026-11-15|技术
|Post Views:

一句话：agent 调模型不是一次「请求—响应」，而是一个带状态的循环。Anthropic Messages、Chat Completions、Responses 三种 API 的差别，本质上是在回答同一个问题——这段对话的状态由谁来存。

整理自 B 站视频：《常用大模型 API 与消息结构》（Agent 开发系列课程 第四课）。

原文按「Anthropic → Chat Completions → Responses」的顺序讲，我按同样的顺序写，但把每家的字段含义、结束状态的判断方式、以及多轮对话到底该传什么补齐了。

为什么这块要单独学

普通的「调个 API 问一句话」，看两眼文档就能跑。但 agent 不一样：

这个循环里，API 必须能把四件事表达清楚：

  1. 谁在说话：系统、用户、模型、还是工具返回的结果；
  2. 内容是什么形态：纯文本、图片、结构化数据、函数调用、推理过程；
  3. 下一步要做什么：正常结束、被截断、要调工具、还是中途出错；
  4. 上一轮发生了什么：要么你把历史全带上，要么告诉服务端一个 id 让它自己找。

前三条决定了消息结构，第四条决定了 API 的形态差异——这正是三种 API 最本质的分界。

好在这个领域没有真的分裂：OpenAI 和 Anthropic 的先发优势太大，绝大多数厂商都提供兼容这两家的端点。把这两家的消息结构学明白，市面上大部分模型都能直接调；剩下的差异通常只是模型名和 base_url。

调用前只有两个配置

任何 SDK 初始化之前，都要先解决两件事：

  • API Key：身份凭证。
  • base_url：服务地址。SDK 会在它后面拼 /v1/messages、/v1/chat/completions 这类路径。

两种配置方式，选一种即可。

项目级：.env 文件

SDK 认的变量名是固定的：OpenAI 系读 OPENAI_API_KEY / OPENAI_BASE_URL，Anthropic 读 ANTHROPIC_API_KEY / ANTHROPIC_BASE_URL。

全局级：写进 shell 配置

全局配好之后，所有项目都不用再写 .env，也不用 load_dotenv()。

两者同时存在时，全局优先。 原因是 python-dotenv 的 load_dotenv() 默认 override=False——已经存在的环境变量不会被 .env 覆盖。想让某个项目的 .env 反过来压过全局，得显式写：

这个坑很隐蔽：明明在 .env 里改了 key，跑起来却还是旧的行为，十有八九就是这里。用第三方兼容服务时也是同理——把 base_url 指向对方的兼容端点、key 用对方的，SDK 侧不用改任何代码。

Anthropic Messages

所有交互都走 messages.create 一个入口，结构非常规整。

请求

四个必须记住的点：

  • max_tokens 是必填的，没有默认值。它限制的是「最多生成多少 token」，不是「一定生成多少」。
  • system 在消息数组外面，是独立参数。这是 Anthropic 和 OpenAI 最直观的结构差异。
  • messages 必须以 user 开头，且 user / assistant 交替出现。 连续两条同角色的消息会被服务端合并成一条，不会报错，但历史语义就变了。
  • content 可以是字符串，也可以是 block 数组。 需要图文混排、工具调用、推理过程时都要写成数组，每块带自己的 type（text、image、tool_use、tool_result、thinking）。

响应

content 是个数组，这点和 Chat Completions 不同——一轮回复可能是「一段思考 + 一段正文」，甚至「一段正文 + 一次工具调用」。打印正文时不能直接 resp.content，要按 block 的 type 过滤：

stop_reason 是判断「这一轮算不算正常结束」的唯一依据：

值 含义
end_turn 正常说完，可以展示给用户
max_tokens 撞到 max_tokens 上限，输出被截断
stop_sequence 命中了你传入的自定义停止序列
tool_use 模型要求调用工具，该执行了
model_context_window_exceeded 上下文窗口先用完了（和 max_tokens 要分开处理）

最后一个是较新的状态：它和 max_tokens 都会导致截断，但原因不同——前者是你把预算给少了，后者是输入本身就快把窗口塞满了，处理方式也不同。

usage 里除了输入输出 token，开了 prompt caching 还会有 cache_creation_input_tokens / cache_read_input_tokens，两者计费不同，做成本统计时要一起算。

多轮对话

模型没有记忆，上一轮的全部内容都要自己带回去——包括你问的，和它答的。

注意 content 回传的是整个 block 数组，不是提取出来的纯文本。开了 extended thinking 之后尤其重要：thinking block 里带的 signature 是校验用的，漏掉或者改写成纯文本，下一轮可能直接报错。

OpenAI Chat Completions

最早、也是被兼容得最广的一套。和 Messages 高度相似，差异集中在「system 放在哪」。

请求

system 不再是独立参数，而是 messages 里的第一条。角色一共五种：

role 作用
system 整个会话的全局约束
developer 开发者指令，优先级高于 user、语义更偏「产品规则」
user 用户输入
assistant 模型回复（回传历史时用）
tool 工具执行结果，需要配 tool_call_id

system 和 developer 不是重复概念：前者偏「你是谁」，后者偏「这个产品要求你怎么做」。多数场景用 system 就够了。

响应

choices 是数组（支持 n>1 一次生成多个候选），日常只取 [0]。finish_reason 与 Anthropic 的 stop_reason 一一对应：stop ≈ end_turn，length ≈ max_tokens，tool_calls ≈ tool_use。

推理模型这里有个结构差异。 Chat Completions 只有一个 content 字段，推理内容没地方放，各家补丁不一样：

  • DeepSeek 这类实现会在 message 里并列一个 reasoning_content 字段，和 content 同级；
  • OpenAI 自己的推理模型不返回推理文本，只在 usage.completion_tokens_details.reasoning_tokens 里给出计数。

所以「怎么拿到思考过程」这件事，在 Chat Completions 里取决于厂商实现，不能假设统一的字段。做多轮时，把 reasoning_content 一并回传通常更稳（有些模型需要它来保持推理连续性），但它不属于标准字段，跨厂商时要做好兼容判断。

三个容易踩的点

  • max_tokens 正在被 max_completion_tokens 取代。 新一代推理模型的思维链也算输出 token，老的 max_tokens 语义不够用；给新模型传 max_tokens 会被拒绝或忽略。写代码时两个都留个开关，比硬编码更耐用。
  • content 可能是 None。 模型决定调工具时，正文是空的，别直接 print(choice.message.content)。
  • developer 角色不是所有兼容实现都支持。 一些小厂商的兼容层只认 system，传 developer 可能被静默忽略。

OpenAI Responses

同一家的升级版。推出它的理由很直接：Chat Completions 把文本、推理、工具调用全塞进一个 message 里，字段越加越多，复杂的多轮 + 工具循环就越来越别扭，而且历史必须你自己维护。

文本、推理、工具调用各占一个 item，类型清清楚楚。resp.output_text 是 SDK 提供的便捷属性，直接把所有 output_text 拼成一个字符串，省掉前面那种按 type 过滤的循环。

status 的取值和 incomplete 的原因也要检查：

status 含义
completed 正常完成
incomplete 完成但被截断，看 incomplete_details.reason（max_output_tokens / content_filter）
failed 服务端失败
in_progress 后台任务还没跑完

第二件：服务端帮你存历史

这是 Responses 最有价值的设计，也是它和前两者最根本的区别。

你在 input 里只放了这一句新问题，历史一句都没传——服务端拿到 previous_response_id 之后自己去翻。第三轮继续追问「把预算提高 50」，同样只需要新的 id。

几个必须知道的细节：

  • instructions 不会被存储续接，每一轮都得重新传。它不参与 previous_response_id 的历史。
  • store 默认为 true。 也就是说你不显式关掉，服务端就会保存这次响应（OpenAI 侧保留约 30 天）。这在隐私敏感场景里是个真问题：想不留痕就得 store=False，但 store=False 的响应也不能用 previous_response_id 续接，历史还是得自己拼。
  • 零数据保留（ZDR）的组织里，store 会被强制当作 false，无论你传什么。所以不能把「服务端存历史」当成默认可用的能力，代码里要有降级路径。

兼容实现的差异，比字段差异更麻烦

三种 API 里，Responses 是兼容得最不彻底的一个。很多厂商号称「支持 Responses API」，实际支持程度差别很大：

  • 有的只实现了请求/响应的形状，store 被静默忽略；
  • 有的支持 store 但保留期不同（官方约 30 天，有的平台只给 7 天，过期后续接直接失败）；
  • 有的完全不支持 previous_response_id，必须自己把历史拼进 input。

所以写代码时别假设「既然格式对上了，续接就一定能用」。一个实用的做法是先探测：传 store=True 发一次请求，看返回里有没有可用的 id 和后续 previous_response_id 是否报错，再决定走服务端续接还是本地拼历史。

三种 API 对照

Anthropic Messages Chat Completions Responses
system 位置 顶层独立参数 messages[0] instructions
必填参数 model、max_tokens、messages model、messages model、input
响应主体 content block 数组 choices[0].message output item 数组
正常结束 stop_reason == "end_turn" finish_reason == "stop" status == "completed"
截断 max_tokens / model_context_window_exceeded length status == "incomplete"
工具调用 content 里的 tool_use block message.tool_calls 独立的 function_call item
多轮方式 自己拼 messages 自己拼 messages previous_response_id 或自己拼

一句话选型：

  • 单轮文本、要最大兼容面 → Chat Completions；
  • 要工具循环、多轮、不想自己维护历史 → Responses；
  • Claude 生态、需要 thinking block 或 prompt caching → Messages。

不想写 if/else：用兼容层

真实项目里经常要同时支持几家。手写 if provider == ... 分支很快就会失控，社区因此有了统一封装：

Python：LiteLLM

统一用 OpenAI 的消息格式，靠 provider/model 前缀路由到对应后端，顺带做了重试、fallback、成本统计。

TypeScript：Vercel AI SDK

同样是「换 provider 包、模型名不变」的思路。

什么时候不该用兼容层：需要原生能力的时候。thinking 的 signature、Responses 的 item 结构、prompt caching 的 cache_control，这些在兼容层里经常被抹平或者丢失。快速做一个支持多家的产品用兼容层，做 agent 深度集成就直接用官方 SDK。

几个容易踩的坑

  1. 上下文永远得有人维护。 模型没有记忆，除了 previous_response_id 那一种情况，历史都要你自己带上，并且顺序不能乱。
  2. 截断要单独判断。 三个 API 各有各的字段，漏判的结果是「输出莫名其妙少了一半」还以为是模型不行。
  3. 工具调用的原理三家一致：模型只给出调用意图，执行永远是你的代码。 不同的是「意图」放在哪个字段里——tool_use block、tool_calls、function_call item。
  4. store 是隐私开关，不只是功能开关。 默认开启意味着数据落在服务端；关掉它就得自己拼历史。
  5. base_url 的路径尾缀要看文档。 有的服务要写 .../v1，有的 SDK 会自己拼 /v1，写重了就 404。
  6. 环境变量的优先级：全局 > .env，除非显式 override=True。
  7. 计费口径不同。 输入、输出、缓存读、缓存写是四个价，usage 里的字段要分开累计。

最后

把三种 API 并排看，会发现它们解决的是同一个问题：如何在无状态的 HTTP 请求上，表达一个有状态的对话循环。

Chat Completions 的答案是「你全带上」，Messages 的答案是「你全带上，但内容分块」，Responses 的答案是「我帮你存，你只给 id」。前两者把复杂度推给调用方，后者把复杂度推给服务端（以及账单和隐私条款）。

理解了这条主线，字段名就不用背了——看到任何一家新出的兼容 API，先找三样东西：system 在哪、结束状态叫什么、历史怎么带。
