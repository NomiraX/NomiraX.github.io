Token 与 Context Window

Created2026-11-15|Updated2026-11-15|技术
|Post Views:

agent 的成本和失败，大半都写在这两个词里：token 决定你花多少钱，context window 决定你在第几轮开始出错。

整理自 B 站视频：Token 与 Context Window

为什么这两个概念在 agent 里格外要紧

普通问答只调一次模型，上下文是一个定值。agent 不一样：它每一轮都要把系统提示、全部历史、工具定义、工具结果重新发一遍，轮数越多，单次请求的输入越长。

于是有两个问题同时出现：钱和窗口。token 决定每次调用怎么计费，context window 决定一次调用最多能装多少。不理解这两个概念，就没法理解后面所有的上下文管理技巧、记忆机制、RAG 和长任务设计——它们本质上都是在处理“窗口有限”这一件事。

token 是什么

模型不直接处理文字。输入文本先经过分词器，被切成一个个小片段，每个片段就是一个 token。

切分规则不是“一个字一个 token”，也不是“一个词一个 token”。它是模型训练时学出来的，可能一个字一个、两个字一个、一个单词的一部分、甚至一个生僻字拆成几个字节片段。所以同一句话在不同模型上切出的 token 数往往不同——词表和规则都由各家的 tokenizer 决定。

切完之后是一连串变换：

token 是这整条链路的中间产物，也正因为如此，它成了最自然的计量单位和计费单位。

几个常见误解值得先破掉：

  • 一个 token 约等于 0.75 个英文单词，或者中文里大致一到两个汉字一个 token，但这只是统计上的手感，具体文本差别很大；
  • 代码和 JSON 更费 token：缩进、括号、引号、换行都会被切，同样的字符数往往比自然语言用掉更多 token；
  • 生僻字、emoji、罕见符号更贵：词表里没有，会被拆成多个字节级 token。

想准确知道一段文本多少 token，不要估，直接用工具算：OpenAI 的 tiktoken，或者厂商提供的 count_tokens 类接口。

输入 token 与输出 token

API 的用量统计总是分成两栏，因为它们价格不同、也对应完全不同的计算过程。

输入 token 是你发过去的一切：

  • 系统提示词；
  • 全部历史消息（user 和 assistant）；
  • 工具定义与参数的 JSON Schema——每一轮都要重发；
  • 工具的执行结果；
  • 贴进去的文档、检索到的片段。

输出 token 是模型生成的一切：

  • 最终回答；
  • 工具调用的函数名和参数（这部分也计费，而且经常被忽略）；
  • 如果开启了思考/推理模式，思考过程也算输出。

注意最后一条：现在很多模型的思考过程是单独返回的字段，但计费上仍按输出 token 算。开不开思考、思考多长，对账单的影响非常直接。

为什么输出比输入贵

同一个 token，输出通常比输入贵 3 到 5 倍。原因在推理的两个阶段。

prefill（预填充）：把整段输入一次性并行算完，生成 KV cache。所有输入 token 一起过一遍，模型权重只读一次，GPU 的算力能吃到接近饱和。这个阶段是计算密集型的，效率很高。

decode（解码）：一个 token 一个 token 地生成。每生成一个，都要把模型权重和之前累积的 KV cache 再读一遍，然后只产出一个 token。这个阶段是访存密集型的，GPU 大部分时间在等数据搬运，算力用不上。输出越长，这个低效过程重复越多次。

一句话概括：输入是批量的并行计算，输出是串行的逐字生成，后者对硬件的利用率低得多，所以更贵。

顺着这个逻辑还能推出两件事：

  • 输出长度对成本的影响比输入更敏感，让模型“简短回答”是真的省钱；
  • 输入虽然便宜，但 agent 每轮都全量重发，量堆起来同样可观。

两种缓存，别搞混

这两种缓存都叫 cache，但作用范围完全不同。

KV cache 是单次推理内部的优化。解码到第 n 个 token 时，前 n-1 个 token 的注意力键值对已经算好，直接复用即可。它只活在这一次请求里，请求结束就没了。

prompt caching（提示词缓存）是跨请求的。上一次请求算出的前缀 KV 被服务端留着，下一次请求如果前缀一模一样，就直接复用这部分计算，只算新增的部分。

为什么可以这样复用？因为 decoder-only 模型用了因果掩码：每个 token 只能看到自己和之前的位置，看不到后面。所以你在前缀后面追加内容，前缀那部分的计算结果不受影响。这正是 agent 场景的常态——messages 数组只追加、不改动，前面那一大段天然稳定。

命中缓存后，输入侧单价通常会降到十分之一甚至更低。各家机制不同：

提供方 触发方式 关键约束
DeepSeek 自动，按前缀块匹配 无需改代码，前缀稳定即可命中
OpenAI 自动前缀缓存 前缀至少 1024 token，缓存保留几分钟到一小时
Anthropic 显式 cache_control 标记断点 写入要额外付费，读取约为十分之一；TTL 可选

这里有个直接影响写法的结论：前缀必须稳定。前缀里改一个字，后面的缓存全部作废。所以：

  • 系统提示、工具定义放最前面，它们是天然稳定的最大前缀；
  • 不要把时间戳、随机 ID、每轮变化的排序结果放在提示词开头；
  • 不要把“重新格式化一遍历史消息”当成常规操作，格式化会让前缀全变；
  • 这也是为什么上下文压缩不能太频繁——每压缩一次，缓存就重建一次。等上下文涨到窗口的七八成才压一次，是有账算的做法。

context window 是一个共享容器

很多人以为 context window 是“输入上限”，其实它是输入加输出的总和。模型一次调用能处理的总 token 数就是窗口大小，中间怎么分配由你决定。

主流模型从 128k 到上百万 token 不等。看起来很大，但对 agent 来说消耗速度是惊人的：

  • 一个工具定义几百 token，十个工具就是几千；
  • 一轮工具结果可能是几千 token（读文件、查日志、接口返回）；
  • 历史消息只增不减。

超限的后果有两种，都很糟：

  1. 请求被拒绝：直接报错，任务中断；
  2. 静默裁剪：服务端按它的规则截断，你不知道它丢了哪一段。丢的可能恰好是任务目标或关键约束，agent 会开始做出莫名其妙的行为。

第二种更危险，因为它是无声的。

还有一个实操上常被忽略的点：窗口是共享的，所以你能用的输入上限 = 窗口大小 − 你给输出预留的空间。如果 max_tokens 设得很大，实际可用的输入空间就相应变小。做长文档处理时，要按“窗口减去预留输出”来算能塞多少内容。

一个能看见增长过程的实验

视频里用一个日志排查 agent 演示了消耗速度：给它一个排查任务，五轮里每轮塞进一页日志（约 2880 字符），并让模型逐页分析。

第一轮，系统提示加用户问题才几十个字符，窗口占用 0.15%；第二轮 0.28%；到第五轮已经是 0.69%。五轮就吃掉了七成窗口，而真实的日志排查往往要几十轮。

这里的成本结构还有个特点：每轮都把历史全量重发，所以第 n 轮的输入包含前 n-1 轮的内容。总输入量大致随轮数平方增长。前缀缓存能把这笔账压下来不少，但只要有一轮改了前缀（比如压缩了历史），缓存就要重建。

context engineering 在管理什么

问题来源很简单：agent 运行时，系统指令、工具、历史、外部知识、长期记忆都在往上下文里灌，而窗口是有限的。

所以要做的事只有两件：控制塞进去的量，保住任务需要的关键信息。常见手段有五类：

策略 做法 代价
滑动窗口 只保留最近 N 轮对话 早期信息直接丢失，可能丢掉目标
压缩摘要 把早期内容压成摘要，保留决策和结论 摘要本身有信息损失，且会让缓存失效
按需检索 文档、知识、历史记录放外部，需要时再召回 依赖检索质量，召回错了全错
复用计算 利用 prompt caching 复用稳定前缀 前缀必须稳定，不能频繁重排
状态外置 进度、中间结果存到外部存储，按需取回 要自己设计状态结构

实践中这几种是配合用的，而不是选一个：最近几轮保留原文（滑动窗口），更早的压成摘要，参考资料放外部按需检索，系统提示和工具定义永久固定在前面吃缓存。

这里也能解释一个看似矛盾的经验：压缩并不是越频繁越省钱。压得太勤，缓存次次失效，每轮都在全额付费重算前缀，反而更贵。

memory、skill、RAG 都来自同一个限制

这三个词经常被当成三个独立技术点，其实它们的出发点完全相同：窗口有限，不能把所有东西都放进去。

memory 解决跨会话的问题。会话结束上下文就没了，所以把用户偏好、历史事实、任务摘要存到外部，下次需要时再放回来。

skill 解决“套路太多”的问题。如果把所有操作手册都塞进系统提示，光定义就占满窗口。做法是渐进式披露：一开始只给模型一句描述“这个技能是干什么的”，它判断需要时再加载详细内容。更进一步，具体执行往往交给本地脚本，脚本跑完只把结果返回——中间过程根本不经过模型，一个 token 都不花。

RAG 解决外部知识的问题。企业知识库动辄几十万文档，全塞进去窗口瞬间爆掉，所以用向量检索只召回相关片段，放进上下文。

理解了“窗口有限”这个共同前提，这三个技术就不用死记了——它们只是三种把信息挡在窗口外面的方式。

实操清单

给自己的项目做体检时，按这几条走：

  1. 量一遍：用 tiktoken 或厂商接口，把系统提示、工具定义、一次典型历史各占多少 token 算清楚，很多问题一算就露出来了。
  2. 看账单的两个数：每次请求记录 prompt_tokens 和其中缓存命中的部分（响应里的 cached_tokens 之类字段），命中率低就是前缀不稳定。
  3. 设阈值：窗口占用到 70%~80% 触发压缩，且压缩放在任务段落边界，不要每轮都做。
  4. 精简工具集：工具定义每轮都进输入，用不到的工具不要挂上；能拆成多个小 agent 的场景，别让一个 agent 背二十个工具。
  5. 控制输出：用输出上限和“简短回答”的指令压输出长度，这是单位成本最高的一栏。
  6. 预留输出空间：算输入预算时，从窗口里先减掉给输出留的部分。

小结

  1. token 是模型处理文本的中间产物，也是计费单位；输出 token 比输入贵，因为解码是逐 token 的访存密集型过程。
  2. prompt caching 复用跨请求的稳定前缀，能把输入成本压一个数量级——代价是前缀不能动。
  3. context window 是输入加输出共用的容器，agent 每轮全量重发，不做管理必然超限，而超限的静默截断比报错更危险。
