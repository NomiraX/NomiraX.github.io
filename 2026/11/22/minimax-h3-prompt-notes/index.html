MiniMax H3 提示词工程笔记：两种写法、六段结构与一套可复现模板

文章发布时间:
2026-11-22

H3 的提示词坑，九成来自同一个误解：以为只有一种写法。实际上「走官网/API」和「跑本地开源权重」是两套语言——前者有 Context-IR 在环内，后者没有。混着写，就是镜头翻倍、台词乱语、参考失效的来源。

这篇笔记把官方规范、开源实测和几篇有数据的社区文章并到一起，目标是：先知道自己在哪一岔，再拿到一套能直接套用的结构。

主要来源：官方 skill 仓库与 HF 模型卡、ComfyUI 官方文档、sceneworks 开源权重实测、阿里云《问道无极》制作实测、Kapwing 方法论、海螺官方知识库。文末给了分档的教程清单。

一、系统分三步，写法因此分成两岔

完整的 H3 不是「一个模型」，而是三段流水线：

模块 职责 是否开源
H3-Context-IR 理解自由多模态输入，把意图与素材关系重写成结构化表示（就是下面那些字段），并补全欠明确处 否，仅托管 API
H3-Base 依据结构化表示生成 768p 有声视频 是（FL2VA / Ref2VA 两个 checkpoint）
H3-Regenerate-2K 把 768p 结果连同原始上下文一起回炉，重生成 2K 否，仅托管 API

官方在模型卡里说得很直白：Context-IR 对最终质量至关重要，强烈建议纳入管线。这句话直接决定了两种写法：

你的环境 正确写法 写错的后果
官网 / 开放平台 API 中文自然语言，只补决策（时长、画幅、谁在做什么、怎么拍、有什么声音） 手工套英文结构化模板 → 和 Context-IR 打架，镜头数翻倍、时间码错位
本地 ComfyUI / SGLang / diffusers 完整英文结构化格式，字段名与标签逐字精确 写散文自由文本 → 台词乱语、角色漂移、音效错位

一句话记：有 Context-IR 时，你写的是「拍摄需求」；没有时，你写的是「Context-IR 的输出」。

二、先记住这张硬约束表

项目 规格
时长 4–15 秒（整数秒）
帧率 24 FPS，写不写都一样
分辨率 短边默认 768；2K 需走 Regenerate-2K
音频 32 kHz 立体声，与画面同一次生成
宽高比 21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16（+ adaptive）
参考图 ≤ 9 张
参考视频 ≤ 3 段，每段 2–15 秒，合计 ≤ 15 秒
参考音频 ≤ 3 段，每段 2–15 秒，合计 ≤ 15 秒
文件总数 所有类型合计 ≤ 12
对白语言 稳定支持 11 种：中、英、日、韩、法、德、意、葡、俄、阿、西
首尾帧 vs 参考素材 不能放在同一个请求里，只能二选一
纯文生 必须指定具体 ratio，不能 adaptive

两个流传很广的误区，顺手记一下：

  • 「采样步数 28–32、CFG 7–8」是 Stable Diffusion 的概念，托管 API 根本没有这两项，填了不生效。
  • 「必须写 24fps」没有意义，帧率是固定的；竖屏要选 ratio: 9:16，不是填像素尺寸。

三、base 模式：一条对齐指令 + 三个字段

base 覆盖 T2VA / I2VA / FL2VA / L2VA 四种模式。结构永远是：

对齐指令是固定句式，不要改写：

  • I2VA：For the target video, at 0.00 seconds into the target video, <Picture 1> (from [Shot 1]) is fully referenced.
  • FL2VA / L2VA：How the reference pictures align with the target video — Picture 1 (from Shot 1) aligns with the 0.00-second mark of the target video; Picture 2 (from Shot N) aligns with the S.SS-second mark of the target video.

其中 S.SS 必须两位小数，且等于成片时长；N 是实际最后一个镜头的编号。

四个模式的区别只在「从哪出发」：

模式 输入 提示词该写什么
T2VA 纯文本 从零构建完整音画时间线
I2VA 一张首帧 从这一帧往后发展，别重复描述已经定下的长相
FL2VA 首帧 + 尾帧 描述两者之间的连续路径，写清「什么在变、什么不变」
L2VA 一张尾帧 反推一个合理开头，逐步收敛到给定尾帧

四、分镜与时间码

这是 H3 相对上一代最实质的变化：一条提示词可以写多个镜头，模型自己切。

规则：

  • [Shot 1] 不带时间码；从 [Shot 2] 起每个镜头都必须带，且严格递增、不超出时长。
  • 切镜动词只有这几个：the camera cuts to / the shot cuts to / transitions to / changes to / switches to。
  • 只是景别或轻微角度变化，优先用运镜，不要切镜。
  • 每次切镜都要带来新信息（主体、空间、状态、视角、时间），否则就是废镜头。

这不是风格偏好，是有实测支撑的。sceneworks 在同一 seed、同一 geometry 下做过 A/B：结构化写法里的 [Shot 2] At 00:03.000, the shot cuts to a closer low-angle view... 能在 3.000 秒 ±1 帧处硬切；改成散文描述则完全不切。附带效果是画面更锐、运动更多、声轨更响更宽。

镜头数有个甜区：一条提示词塞 8–12 个镜头还算稳，超过就开始丢镜头，该拆成分段生成了。

五、运镜词表

官方把运镜拆成三个维度：类型 + 幅度 + 速度。中等幅度与常速省略不写。

类型 含义
Zoom In / Out 变焦，机身不动
Push In / Pull Out 机身前后移动
Pan Left / Right 水平摇
Truck Left / Right 水平平移
Tilt Up / Down 俯仰摇
Pedestal Up / Down 升降
Arc Shot 环绕
Tracking Shot 跟随
Static Shot 固定机位
Shake Slightly / Strongly 抖动
POV 主观视角
Roll Clockwise / Counterclockwise 滚转

幅度写 with small amplitude / with large amplitude；速度写 at slow speed / at fast speed。

要写成镜头内的自然英文句子，不要句尾堆标签：

两条容易踩的：

  • 不写运镜 = 固定机位死镜头。模型不会替你加运动。
  • 一条提示词只给一个主导运动。同时写「先加速再减速」「推+摇+跟」，结果是抖动与物理幻觉——这是海螺官方知识库里明确点出的 token 干扰问题。

六、台词、说话人与声音

说话人

  • 稳定 ID：(S1)、(S2)；两人同时说话写 (S1,S2)。
  • 首次出现要交代：年龄、性别、是否在画、音高、音色、语速、口音。
  • 台词放在 <d> 里，<d> 内只放 [语言] + 逐字原文，不改写、不翻译。识别短语、ID、动作、语气都放外面：
  • 旁白固定短语 says in an off-screen voiceover，且 <d> 后必须紧跟 while her lips remain completely closed。
  • 台词跨切镜用 <scenetrans> 并说明音频连续；被片尾截断用 <cutoff>。
  • 画面内可见文字用英文双引号原样保留，例如 "营业中"。
  • 听不清写 [unclear]，不要猜。只拿音色参考时，不要搬用原台词的语义。

三条声音线别写混

字段 写什么 不写什么
integrated_multimodal_description 画面内、角色能听到的声音（diegetic） 配乐
overall_soundscape 1–4 句：环境底噪 + 物理动作音 + 非语言人声（喘息、脚步） 台词、歌声、剧内音乐（已在主描述里）
non_diegetic_music 1–3 句：乐器、速度、节奏、力度变化 抽象情绪词、解释配乐功能

只有用户明确要求全片静音，overall_soundscape 才写 N/A；没有配乐，non_diegetic_music 写 N/A。

「不写声音」是最常见的底噪来源：H3 音画一次生成，你不交代，它自己发挥。

七、Ref2VA：六段式与四种标签

多素材参考（图 / 视频 / 音频混合）走 Ref2VA，段落顺序固定，不可调换：

四种标签，各管一件事

标签 用在
<Subject N> 可复用的可见内容：人、动物、物、场景、服装、道具、界面、风格、动作、表情、姿势。可由多个素材共同定义
<Picture N> 只有当它被当作具体帧 / 关键帧 / 构图锚点时才单列；仅用于定义角色、场景、风格时，写进 Subject 定义里
<Video N> 整段视频关系：编辑源、续写起点、运镜 / 剪辑 / 节奏结构
<Audio N> 音频信号：复制、风格、音色、台词、节拍

<Video N> 与 <Audio N> 独立编号，同一素材可以是 Video 1 + Audio 2。

summary 与 retention

summary 以方括号任务类型开头，多种关系用 + 连接且不重复：

retention_analysis 用固定英文枚举，一个标签一行，格式为「标签 + 出现镜头 + 标记 + 理由」：

类别 合法取值
视觉 fully_preserved / partially_preserved / attribute_transfer / weak_reference
音频 fully_copy / partially_copy / reference / weak_reference

detailed_description

生成任务通常 350–500 英文词。台词密集时，以「装得下完整台词时间线」为优先，可以超；视频编辑则按源素材复杂度伸缩。

写法要点：

  • 说话人写成 <Subject 2> (S1) turns toward...
  • 音色参考写成 <Audio 1> is the voice-timbre reference for <Subject 1> (S1).
  • 风格独立成句，放在 [Shot 1] 之前。

格式错误里最高频的一种是悬空标签：正文引用了 <Picture 3>，但 subject_definitions 里从没定义过它。标签编号必须等于实际附件顺序（ref_image_0..8 → <Picture 1..9>），错位等于参考完全失效。

八、托管端：人话六模块

走官网/API 时不要手工结构化，按这六块写中文就行：

要点全是踩过坑的：

  • 动作写过程，不写结论。「她很伤心」是结论，模型拍不出来；「微微低头，缓缓抬眸，眼底含泪，肩膀随呼吸轻轻起伏」才是可拍的。
  • 图生视频只写「接下来发生什么」。 首帧已经定了长相、场景、画幅，再描述外貌会和图打架。
  • 首尾帧只改一两个要素（光线、服装），并写清「什么在变、什么不变」——比只写「自然过渡、画面连贯」有用得多。
  • 多主体先写站位：谁面对谁、谁在画面左/右侧、镜头站在谁身后。只写「人物近景，背景里有野猪」，野猪就会跑到人背后。
  • 长打斗一次生成、内部按时间分镜，各段时长之和等于 duration：
  • 防崩后缀一句就够：画面稳定，人物五官和服饰前后一致，光影统一，动作自然流畅。 接口没有独立负面提示词参数，这话只是普通描述，解决不了提示词本身的问题。

九、减法式：只给一个主导速度向量

海螺官方知识库的思路和上面互补，值得单独记一笔。它主张做减法：一条片子只给一个主导的速度性格。

速度向量 关键词
Explosive Acceleration sudden burst / rapid acceleration / FPV dive
Constant Kineticism steady tracking / consistent glide / uniform drift
Decelerating Impact gradual slow-down / settling into a stop / cinematic deceleration

同时写「先加速再减速」会产生 token 干扰，落地表现是抖动和物理幻觉。真正需要复杂 speed ramp 时，正解是在 NLE 里用两条片段（稳定跟拍 + 高速冲刺）拼接，而不是一句提示词许愿。

另外两条同源经验：I2V 先出高质量静帧再给运动向量；单条片子按 3–5 条 reroll 预算算成本。

十、翻车对照表

症状 病因
台词乱语、念错 没给逐字原文，或 <d> 里被改写
角色不像、越动越漂 身份没锁；参考职责冲突；参考图与首尾帧混用
音色不对 没给音色参考 <Audio N>，或标签顺序与附件顺序不一致
音效错位 声音没绑到时间点
参考完全没生效 标签编号 ≠ 附件顺序；出现悬空标签
镜头乱晃 一条提示词写了多种运镜
莫名底噪、自带 BGM 声音完全没交代
9 张图互相打架 没给每张图派活，也没写它该忽略什么
运镜复刻了但人变了 没区分不变量与变量
身份锁不住 脸部占画面太小 → 用广角交代场景、近景/中景演戏

十一、成本与迭代纪律

项目 价格（以账单为准）
H3 768P 0.5 元/秒
H3 2K 0.8 元/秒
2K 再生成 0.3 元/秒
Context-IR 增强 按 token 计费，一次约几分钱

所以标准流程是：768P 试 → 满意再升 2K。一条 5 秒镜头，768P 是 2.5 元；先出 768P 再转 2K 合计约 4 元，和直接出 2K 同价，好处是不满意的镜头在便宜阶段就被淘汰。

成本的大头从来不是单价，是返工次数。

本地权重还有几条自己的约束（来自 sceneworks 实测，非厂商口径）：

  • 合法时长只有 14 个档位：5.17 / 5.88 / 6.58 / 7.29 / 8.00 / 8.71 / 9.42 / 10.13 / 10.83 / 11.54 / 12.25 / 12.96 / 13.67 / 14.38 秒（帧格 17n+5）。宣称的 15 秒落在档位之间，渲染不出来。
  • 画布按约 1.03MP 的面积预算算，1344×768 是默认全尺寸。
  • 没有 guidance、没有负面提示词参数 → 只能正面表述（不说 blurry，说 sharp, crisp focus；不说 no music，说 no non-diegetic music, room tone only）。
  • <d>、<cutoff>、<lyrics_start|end> 这些标记在开源权重里是无效 token，台词得改写成普通文本。
  • Turbo 4-step 适配器能把 1344×768 / 5.17 秒从约 2 小时 25 分压到 12.6 分钟，但那是另一次采样，不是同一画面的加速。

怎么识别营销号内容

四个特征够用：通篇形容词没有一个参数；没有 A/B 对照只放最好那条；把 SD 的 steps/CFG 套到托管 API 上还说「这样最稳」；通篇不提 integrated_multimodal_description、<d>、retention 这些真实字段，只给「万能公式」。

十三、上手路径

  1. 读官方 base-en.txt + ref-en.txt，半小时建立坐标系。
  2. 看官方 README 那三个 Context-IR 输出案例，知道「标准答案」长什么样。
  3. 抄一条最接近的模板，跑 768P。
  4. 给自己做一次 A/B：同一剧情，大白话版 vs 结构化版，各跑一条。做完这一步，直觉会超过看十条教程。
  5. 要本地跑，再进 ComfyUI 官方文档的六个子页。

最后一条心法，来自那条 A/B 视频，也是整篇笔记的收束：

提示词不是在写作文，是在写一份给导演、摄影师和演员看的拍摄说明。目标只有一个——少让模型猜。
